# 变更记录 Skill - 演示汇报说明

## 概述

`change-tracking` 是项目变更留痕的项目级规范 Skill。

它负责判断一次修改应该记录到就近模块 `CHANGELOG.md`，还是升级到 `docs/变更记录/`。它解决的是“以后为什么这么改、影响了哪些规则、排查时去哪里看”的问题。

## 核心能力

- 区分小修改和大修改。
- 小修改优先记录到最近模块目录下的 `CHANGELOG.md`。
- 需求、架构、规范、跨模块、跨前后端、数据库结构或可追溯 Bug 修复等变更，升级记录到 `docs/变更记录/`。
- 维护 `docs/变更记录/CHANGELOG.md` 总索引。
- 按类型补充 `规范变更.md`、`需求变更.md`、`架构变更.md`、`问题修复.md` 等分类文档。
- 避免把 Git 历史当成变更说明的唯一来源。

## 工作流程演示

1. 判断当前任务是否需要留痕。
2. 判断影响范围：单模块小改，还是需求、架构、规范、数据库或跨模块变更。
3. 小修改写入就近模块 `CHANGELOG.md`。
4. 大修改写入 `docs/变更记录/CHANGELOG.md` 和对应分类文件。
5. 记录内容包含变更原因、影响范围、关键决策和验证情况。
6. 如果命中需求实现或数据库场景，联动对应需求记录和 DataSQL 文档。

## 典型场景

- 修改 AI 开发 SOP、AGENTS 或项目级 Skill。
- 调整前后端协作边界、目录规范或模块命名规则。
- 修复一个会影响后续排查的 Bug。
- 改动数据库结构或通用 SQL 约定。
- 对需求口径、实现计划或验收标准做了调整。

## 与其他 Skill 的联动

- `requirement-implementation-tracking`：需求实现记录负责业务需求落地细节，`change-tracking` 负责项目级变更原因和影响。
- `database-schema-standard`：数据库变更需要 DataSQL 正式留痕，同时通常也需要项目级变更摘要。
- `backend-development-standard`：后端改动完成后，如果影响范围达到升级规则，补充变更记录。
- `project-init`：初始化脚手架时涉及大量命名和规范收敛，需要同步变更记录。

## 禁止事项

- 不要只写“已修改”而不写为什么改、影响什么。
- 不要把规范类变更只放到模块 `CHANGELOG.md`。
- 不要用 Git 提交信息替代项目变更记录。
- 不要在无关小改中制造过度留痕，但出现公共规则变化时必须升级记录。
