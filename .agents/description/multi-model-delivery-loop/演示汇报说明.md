# 多模型交付闭环 Skill - 演示汇报说明

## 概述

`multi-model-delivery-loop` 是当前项目中面向多模型协作开发的项目级 Skill。

它适用于这样一种分工：`规划复核角色` 负责拆需求、定计划、做复核，`实现修复角色` 负责实现代码和定向修复。它不直接自动切换模型，而是把切换动作规范化、文档化、可追踪化。

## 核心能力

- 把多模型协作明确成“规划 -> 实现 -> 复核 -> 修复 -> 再复核”的闭环。
- 约束 `规划复核角色` 与 `实现修复角色` 的职责边界。
- 在 `docs/需求/需求包/*/实现进度.md` 中记录当前阶段、当前责任角色、当前执行工具和下一责任角色。
- 在交接点输出固定的“模型切换提示”，并停下来等待用户手动切换模型。
- 为每次切换生成明确的交接提示词模板。
- 在复核未通过时记录问题说明和修复建议，避免返工过程失控。
- 用表格化复核记录支持多轮复核，而不是只写一句“通过 / 不通过”。

## 工作流程演示

1. 先由 `requirement-implementation-tracking` 生成需求包计划。
2. 在 `实现计划.md` 中补角色协作策略。
3. `规划复核角色` 负责当前模块的规划、步骤定义和验收口径。
4. 文档中标记下一责任角色为 `实现修复角色`，并产出交接提示词。
5. `实现修复角色` 实现代码后，将状态切为“待规划复核角色复核”。
6. `规划复核角色` 按需求、目录、测试和留痕规则复核。
7. 通过则完成；不通过则写问题说明和修复建议，再切回 `实现修复角色`。

## 典型场景

- 当前环境无法自动切换模型，但希望把切换动作流程化。
- 需求复杂，希望用规划复核角色负责规划和验收，用实现修复角色负责实现细节。
- 一个模块需要多轮修复，想清楚知道每轮问题是什么、当前卡在哪一步。
- 需要让需求包进度文档不仅记录状态，还能直接指导下一位模型接着做什么。

## 与其他 Skill 的联动

- `requirement-implementation-tracking`：先拆需求、建模块总表和需求包，再进入多模型交付闭环。
- `backend-development-standard`：实现修复角色实现后，复核时仍需按后端目录和分层规范检查。
- `database-schema-standard`：涉及数据库时，复核要同时检查 DataSQL 和数据库留痕索引。
- `change-tracking`：如果多模型协作流程本身引起规范变化，需要补项目级变更记录。

## 限制说明

- 这个 Skill 不直接控制底层模型切换。
- 在没有外层编排器时，它是“半自动协作规程”，不是“自动模型路由器”。
- 它的价值在于让文档明确提示下一步切到哪个角色、做什么、验什么，而不是口头来回切。

## 禁止事项

- 不要声称 Skill 已经自动完成模型切换。
- 不要只切模型不记文档，导致后面看不出当前责任和问题回环。
- 不要让实现修复角色自行改变需求目标或扩大重构范围。
- 不要让规划复核角色复核只看代码，不看需求包计划、测试和留痕。
