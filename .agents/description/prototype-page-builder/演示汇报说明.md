# 原型页面构建 Skill - 演示汇报说明

## 概述

`prototype-page-builder` 是为产品经理、评审方或需求讨论场景快速产出可浏览原型站点的项目级 Skill。

它和正式前端开发不同：原型默认落在 `docs/原型站点/`，用于需求表达、交互展示和评审沟通，不直接进入 `code/frontend/`。

## 核心能力

- 使用统一 layout、菜单配置和 iframe 页面加载方式组织原型站点。
- 在 `pages/*.html` 中快速新增业务页面。
- 通过独立菜单配置维护页面入口。
- 复用原型模板、样式和脚本，不污染正式前端工程。
- 明确区分“产品原型开发”和“正式前端开发”。

## 推荐目录示例

```text
docs/原型站点/
├── index.html
├── assets/
├── config/
│   └── menu.js
└── pages/
    └── dept-list.html
```

## 工作流程演示

1. 判断用户目标是否是给产品或评审直接看原型。
2. 读取根目录 `AGENTS.md` 和 `prototype-page-builder/SKILL.md`。
3. 复用原型目录、layout、菜单配置和页面模板。
4. 新增或调整 `pages/*.html` 页面。
5. 更新菜单配置。
6. 使用浏览器或静态检查验证页面可访问。
7. 如果原型影响需求实现口径，联动 `requirement-implementation-tracking` 记录需求来源或原型依据。

## 典型场景

- 快速做一个部门管理、字典管理、流程配置等页面原型。
- 为需求评审准备可点击的页面集合。
- 在正式前端开发前确认信息架构、字段和交互。
- 根据产品反馈快速调整页面布局和文案。

## 与其他 Skill 的联动

- `requirement-implementation-tracking`：原型是需求拆分的重要输入之一，可作为需求包来源。
- `change-tracking`：如果原型规范或项目级原型目录规则发生变化，需要留痕。

## 禁止事项

- 不要把产品原型误做进 `code/frontend/`。
- 不要把原型任务导向 `docs/superpowers/specs/`。
- 不要每个页面复制一套独立 layout，导致菜单和样式不可维护。
- 不要把原型当成正式前端代码的质量和构建边界。
