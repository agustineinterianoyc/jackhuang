# 需求拆分与实现计划 Skill - 演示汇报说明

## 概述

`requirement-implementation-tracking` 是当前项目需求开发前置规划和实现留痕的项目级 Skill。

它已经从单纯的“需求实现记录”升级为“读取需求/原型 -> 自动拆分业务模块 -> 维护项目模块总表 -> 生成需求包计划 -> 按模块记录实现进度”的完整体系。

## 核心能力

- 从 `docs/需求/` 和 `docs/原型/` 读取输入。
- 根据需求文件、原型页面和业务语义自动拆分模块。
- 维护 `docs/需求/模块总表.md`，统一模块中文名、模块编码、后端目录名和 DataSQL 目录名。
- 为每次输入的一批需求、一个版本或一次迭代生成需求包计划。
- 在 `docs/需求/需求包/<需求包>/实现计划.md` 中记录整体目标、模块范围、开发步骤、依赖顺序和验收重点。
- 在 `docs/需求/模块/<模块>/` 下维护长期模块级需求实现记录、优化调整记录和数据库留痕索引。
- 将后端目录、测试目录和 DataSQL 目录统一到同一模块编码体系。

## 工作流程演示

1. 读取 `docs/需求/` 和 `docs/原型/`。
2. 识别本次需求包的来源、范围和目标。
3. 自动拆分业务模块，判断是否复用已有模块。
4. 先登记或更新 `docs/需求/模块总表.md`。
5. 生成需求包级整体实现计划和分模块步骤。
6. 按模块更新长期需求实现记录。
7. 开发过程中更新实现进度、偏差、调整原因和验收结果。
8. 涉及后端时，把模块编码传递给后端目录、测试目录和 DataSQL 目录。
9. 涉及数据库时，只在需求模块下维护数据库留痕索引，完整 SQL 仍以 DataSQL 为准。

## 典型场景

- 一次性输入一批需求文档，需要 AI 先拆模块再开发。
- 第二期需求继续修改第一期的部门模块，需要复用 `dept` 模块编码。
- 需要知道 AI 当前每个模块做到哪一步。
- 需要把需求、原型、后端目录、测试目录和数据库留痕统一到同一套模块命名。
- 需求实现后要复盘偏差、优化调整和验收结果。

## 与其他 Skill 的联动

- `backend-development-standard`：根据模块总表中的模块编码落后端业务目录。
- `database-schema-standard`：DataSQL 业务目录优先来自模块总表，需求目录只维护数据库留痕索引。
- `change-tracking`：需求体系、实现计划或公共规范变化需要项目级留痕。
- `prototype-page-builder`：原型页面可作为需求包来源之一。
- `using-superpowers`：如果全局 `using-superpowers` skill 被命中，可额外记录 `docs/superpowers/` 链路；未安装或未命中时，不要求记录。

## 禁止事项

- 不要把需求包理解成机械的第一期、第二期孤岛文档。
- 不要绕过 `模块总表.md` 直接创建后端目录或 DataSQL 目录。
- 不要在需求目录重复维护完整 SQL。
- 不要让同一模块在需求、代码、测试和数据库中使用不同命名。
- 不要把 `docs/superpowers/` 当成项目默认必需流程。
