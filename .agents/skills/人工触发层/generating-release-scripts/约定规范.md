# 前后端打包发布脚本约定规范

## 输出目标

必须生成一套用于前后端项目的软件打包发布脚本方案。

这套脚本最少拆分为 4 份，禁止合并成一个大脚本：

1. `check-env`
2. `build-base`
3. `publish`
4. `report`

对于前后端分离项目，优先采用三套模板：

1. 前端脚本集
2. 后端脚本集
3. 总控编排脚本集

总控只负责编排，不承载构建和发布细节。

## 适用范围

- 前端静态构建产物
- 后端目录/压缩包型产物
- Java JAR/WAR 型产物
- Docker 镜像型产物

## 不适用范围

- Helm Chart 复杂发布编排
- 多服务矩阵批量发布
- 云厂商专有发布平台深度集成
- 蓝绿、金丝雀、自动回滚系统
- Windows 原生批处理脚本

## 四份脚本的强制职责

### `check-env`

只能负责环境检查，不能做构建，不能做发布。

必须包含：

- 检查必需命令是否存在
- 检查必需环境变量是否存在
- 检查输入参数是否合法
- 检查目标环境是否合法
- 检查版本号是否提供
- 检查凭证是否存在但不能打印凭证值
- 检查产物目录、工作目录、临时目录是否可用
- 检查网络或目标发布地址是否可达（如果场景需要）

任一检查失败，必须立即退出，退出码非 0。

### `build-base`

只能负责基础构建，不能直接发布。

必须包含：

- 安装依赖或校验依赖
- 执行编译或打包前构建
- 执行测试或最少可用校验
- 生成构建产物
- 将产物输出到固定目录
- 生成产物校验信息

对于后端模板，必须明确交付物类型：

- `archive`
- `jar`
- `docker`

禁止包含：

- 上传制品
- 触发远程部署
- 修改远端发布状态
- 写入正式发布记录

### `publish`

只能负责发布动作，不能重复实现构建流程。

必须包含：

- 读取构建产物
- 校验构建产物存在
- 校验版本号与环境信息
- 执行上传、发布、部署或登记动作
- 在发布前检查目标制品是否已存在
- 对正式环境增加额外保护条件

发布动作分三层：

1. `publish`：上传或推送制品
2. `register`：登记发布记录
3. `deploy`：触发部署动作

生成脚本时必须把三层动作拆清楚，禁止把所有逻辑无区分地混在一起。

必须明确采用至少一种策略：

- 目标制品已存在则失败退出
- 目标制品已存在则校验一致后跳过

禁止默认覆盖已有正式制品。

### `report`

只能负责过程信息输出，不能承载构建和发布动作。

必须包含：

- 输出阶段开始日志
- 输出阶段结束日志
- 输出错误摘要
- 输出结果摘要
- 输出结构化结果，至少包含：脚本名、阶段名、状态、版本号、环境、时间

禁止把实际业务逻辑塞进 `report`。

## 统一实现规则

所有脚本必须同时满足：

1. 必须支持 `--help`
2. 必须支持 `--dry-run`
3. 必须支持明确退出码
4. 必须在脚本开头进行参数校验
5. 必须在失败时立即退出，禁止吞错继续执行
6. 必须有清理逻辑
7. 必须有统一日志函数
8. 必须避免泄露敏感信息
9. 必须保证重复执行时行为可预测
10. 必须使用固定产物目录
11. 必须能追溯版本号
12. 必须区分 `dev`、`test`、`staging`、`prod` 等环境

## 禁止事项

禁止出现以下情况：

1. 把四类职责混在一个脚本里
2. 把高风险命令直接串起来执行而没有保护
3. 不做输入校验
4. 不做错误处理
5. 不做日志输出
6. 把密钥、令牌、密码打印到日志里
7. 硬编码凭证
8. 默认覆盖已有发布制品
9. 默认对生产环境直接发布
10. 在 `build-base` 中直接上传或部署
11. 在 `report` 中夹带业务逻辑
12. 只给伪代码，不给完整脚本

## 语言选择

用户未指定时，默认使用 Bash Shell。

Shell 默认风格：

- 使用 Bash
- 顶部声明 `#!/usr/bin/env bash`
- 使用严格模式
- 提供统一日志函数
- 提供统一退出函数

只有在以下情况才允许改用 Python：

- 需要复杂配置解析
- 需要复杂 JSON 处理
- 需要复杂错误分类重试
- 需要多平台兼容逻辑明显超过 Shell 可维护范围

如果改用 Python，必须明确说明原因。

## 信息不足时的处理

如果上下文不完整，不要乱猜业务细节。

应当：

1. 保留通用占位变量名
2. 在需要用户补充的地方用明显注释标记
3. 仍然输出完整脚本骨架
4. 不得因为缺少少量业务信息就只输出概念说明

## 合格标准

结果至少满足：

- 脚本数量不少于 4 份
- 四份脚本职责边界清晰
- 代码可直接保存执行
- 有输入校验
- 有错误处理
- 有日志输出
- 有 `dry-run`
- 有生产保护
- 有重复执行保护
- 有结构化结果输出
