# 数据库表设计与变更规范

在当前仓库处理数据库表结构设计、DDL 变更和表变更留痕时，按本 skill 执行。

## 开始前

先阅读：

- `code/backend/AGENTS.md`
- `code/backend/aldemo/src/main/resources/application.yaml`

先确认：

- 这次是新增表、修改表、加字段、改字段、删字段、加索引还是改 SQL
- 这次变更属于哪个业务模块
- 该业务模块是否已登记在 `docs/需求/模块总表.md`
- 是否需要在 `code/backend/DataSQL/` 下新增或更新业务留痕文档
- 当前项目实际选中的数据库类型是什么

所有数据库相关改动，都要同时考虑两件事：

1. 结构设计是否规范
2. 变更记录是否留痕

额外再确认一件事：

3. 留痕中的 SQL 是否与当前项目实际启用的数据库方言一致

## 数据库方言判断规则

在生成 DDL、数据修复 SQL、Mapper SQL 或 DataSQL 留痕里的 SQL 代码块之前，先判断当前项目使用的是哪一种数据库。

按以下顺序判断：

1. 先看 `code/backend/aldemo/src/main/resources/application.yaml`
2. 读取 `spring.profiles.active`
3. 读取 `app.database.platform`
4. 如启用了 `application-mysql.yaml`、`application-oracle.yaml`、`application-postgresql.yaml` 之一，以数据库 profile 为准

默认判断规则：

- active profile 中包含 `mysql`：
  按 MySQL 语法生成 SQL
- active profile 中包含 `oracle`：
  按 Oracle 语法生成 SQL
- active profile 中包含 `postgresql`：
  按 PostgreSQL 语法生成 SQL
- active profile 未显式带数据库类型，但 `app.database.platform` 已配置：
  按该平台值生成 SQL

当前脚手架的默认配置是：

- `spring.profiles.active=dev,mysql`
- `app.database.platform=mysql`

所以如果没有额外说明，默认按 MySQL 方言生成 SQL。

如果数据库类型判断不明确：

- 先在留痕文档中写明本次采用的假设
- 再按当前最接近的实际 profile 生成 SQL
- 不要同时混写多种数据库语法

## 目录留痕规则

数据库表相关变更，统一在：

- `code/backend/DataSQL/`

下按业务归档。

目录结构约定：

```text
code/backend/DataSQL/
├── 业务变更汇总清单.md
└── <DataSQL目录名>/
    └── 表设计与变更记录.md
```

规则如下：

- `<DataSQL目录名>/` 优先来自 `docs/需求/模块总表.md` 中登记的 DataSQL 目录名
- 如果模块总表尚未登记该业务模块，先按 `requirement-implementation-tracking` 补齐模块中文名、模块编码和 DataSQL 目录名，再新增 DataSQL 业务目录
- `业务变更汇总清单.md` 记录所有业务层面的数据库变更总览
- 每个业务目录下的 `表设计与变更记录.md` 记录该业务具体涉及了哪些表和哪些动作
- 需求模块目录中的 `数据库留痕索引.md` 只引用 DataSQL 明细，不重复维护完整 SQL、字段清单或索引清单

只要改了表、字段、索引、SQL 结构或表关系，都要同步更新对应文档。

从现在开始，留痕不只记录“改了什么”，还要记录“对应 SQL 怎么写”。

强制要求：

- 业务明细中的表结构、字段、索引、注释、数据回填、兼容处理，必须带对应 `sql` 代码块
- SQL 代码块必须与当前项目实际选中的数据库方言一致
- 代码块里使用的表名、字段名大小写，要与目标数据库规范一致
- SQL 代码块要尽量可执行，不要只写伪 SQL

推荐把业务明细文档设计成四段式：

1. 业务涉及表总览
2. 变更流水总览
3. 单表详细变更记录
4. 附加说明

这样既能先回答“这个业务碰了哪些表”，又能回答“什么时候改了什么”，最后还能落到“某张表的具体历史和 SQL”。

## 表设计基本原则

默认遵循以下原则：

- 表名应由“前缀 + 业务主体名称 + 尾缀”组成
- 表名应带清晰业务语义，不使用含糊缩写
- 字段名要表达真实业务含义，不用过度简写
- 一个字段只表达一个含义，不堆叠多重语义
- 能通过枚举、状态值表达的，不用模糊自由文本代替
- 能拆成明确字段的，不把多个值硬塞进一个字段

不要只为了方便当前功能把表设计成短期可用但长期不可维护的状态。

### 表名规范

表名统一分三段理解：

1. 前缀：
   使用包根中的项目名称
2. 主体名称：
   使用能直接联想到当前业务的语义名称
3. 尾缀：
   按表用途追加约定后缀

示例理解：

- 前缀：
  `training`
- 主体名称：
  `order`
- 尾缀：
  `log`

组合后类似：

- `training_order_log`

命名要求：

- 前缀统一，不要同项目中一会儿 `training` 一会儿 `ai_training`
- 主体名称要让人一眼能联想到业务对象
- 尾缀要表达表用途，而不是随意追加

常见尾缀示例：

- 日志表：
  `log`
- 明细表：
  `detail`
- 关系表：
  `rel`
- 汇总表：
  `summary`
- 历史表：
  `his`
- 扩展表：
  `ext`

如果表本身已经是明确业务主表，可以不强行追加复杂尾缀，但要保证一眼能看出用途。

### 数据库大小写规则

不同数据库遵循不同表名和字段名大小写约束：

- MySQL：
  使用小写表名和小写字段名，例如 `cpp_name`、`order_status`
- Oracle：
  使用大写表名和大写字段名，例如 `CPP_NAME`、`ORDER_STATUS`
- PostgreSQL：
  默认使用小写表名和小写字段名，例如 `cpp_name`、`order_status`

同一个数据库内不要混用大小写风格。

### 长度控制规则

表名和字段名都不建议设计得过长。

控制原则：

- 先保证语义清晰，再控制长度
- 不要为了极短而牺牲可读性
- 也不要把多个限定词全部堆进名称里导致过长
- 名称应做到“看一眼能大概知道用途”，但不要写成长句

命名时优先保留：

- 项目标识前缀
- 业务核心对象
- 关键用途后缀

命名时优先删减：

- 重复语义
- 无信息量的修饰词
- 只在当前上下文才成立的冗余前后缀

### 表注释三步走

表注释默认也按三段式表达：

1. 所属业务
2. 核心对象
3. 表用途

推荐写法：

- `订单业务-订单主表-记录订单基础信息`
- `用户业务-用户日志表-记录用户登录行为`
- `租户业务-租户关系表-记录租户与应用的逻辑关联`

不要只写：

- `订单表`
- `日志表`
- `关系表`

## 主外键与关联规则

当前项目默认不使用数据库层面的主外键约束来建立表关系。

统一使用逻辑关联：

- 在业务层、SQL 层和文档层维护关联关系
- 通过字段命名、注释和留痕文档明确说明关联来源

例如：

- `user_id` 逻辑关联 `sys_user.id`
- `order_no` 逻辑关联 `biz_order.order_no`

字段注释中应显式写出关联目标，例如：

- `用户ID，逻辑关联 sys_user.id`
- `订单编号，逻辑关联 biz_order.order_no`

不要只写“用户ID”或“订单编号”而不标明关联来源。

## 字段设计规范

新增或修改字段时：

- 字段名要准确
- 字段名要和表名的大小写规则保持一致
- 字段名不建议过长
- 字段类型要与业务含义匹配
- 长度、精度、默认值要明确
- 是否允许为空要明确
- 注释必须完整

字段注释至少要说明：

- 字段中文含义
- 业务用途
- 如果是逻辑关联字段，要说明关联哪张表的哪个字段
- 如果是状态字段、类型字段、标记字段，要说明取值语义

推荐注释风格：

- `状态，1-待处理，2-处理中，3-已完成`
- `租户ID，逻辑关联 sys_tenant.id`
- `删除标记，0-未删除，1-已删除`

不推荐：

- `状态`
- `用户id`
- `删除`
- `this_is_a_very_long_field_name_used_only_for_current_page_logic`

### 字段类型选型建议

默认优先按业务语义选型，而不是按“先能存进去”选型。

常见建议：

- 主键：
  使用 `bigint`
- 逻辑关联 ID：
  与被关联字段类型保持一致，通常使用 `bigint`
- 状态、类型、标记：
  优先使用 `int`、`tinyint` 或明确长度的数值类型，不用随意字符串化
- 金额、单价、比率：
  使用 `decimal(p,s)`，不要使用 `float` 或 `double`
- 时间点：
  优先使用 `datetime` 或项目既有统一时间类型
- 长文本说明：
  根据长度需求使用 `varchar` 或 `text`
- 编码类字段：
  使用有明确上限的 `varchar`

避免：

- 用 `varchar` 存本该是数值状态的字段
- 用浮点类型存金额
- 无约束地把所有描述字段都设成超大长度
- 同一语义字段在不同表中使用不一致类型

## 公共字段建议

如果新表是常规业务表，优先评估是否需要以下公共字段：

- `id`
- `created_at`
- `updated_at`
- `created_by`
- `updated_by`
- `deleted`

如果使用这些字段：

- 命名要统一
- 语义要统一
- 注释要统一

不要同类表里一张叫 `create_time`，另一张叫 `created_at`，除非项目已明确采用不同标准。

## 字段命名规范专章

高频公共字段应尽量统一命名，不要同一套工程里混用多套近义名字。

默认原则：

- 新表优先使用统一命名
- 兼容历史表时，如必须沿用旧字段名，要在变更记录中说明原因
- 同一业务域内不要同时出现 `status` 和 `state`、`deleted` 和 `is_deleted` 这类重复标准

### 推荐字段名

- 状态字段：
  `status`
- 类型字段：
  `type`
- 编码字段：
  `code`
- 名称字段：
  `name`
- 备注字段：
  `remark`
- 删除标记字段：
  `deleted`
- 创建时间字段：
  `created_at`
- 修改时间字段：
  `updated_at`
- 创建人字段：
  `created_by`
- 修改人字段：
  `updated_by`

这些字段如果出现在大多数业务表中，优先直接采用以上标准名，不再为相同语义发明新的变体。

### 字段语义约束

- `status`
  表示业务状态、流程状态、启停状态等“当前状态”
- `type`
  表示业务分类、记录类型、来源类型等“类别属性”
- `code`
  表示可对外识别、可枚举或可检索的编码
- `name`
  表示核心展示名称或业务对象名称
- `remark`
  表示补充说明、人工备注、附加描述
- `deleted`
  表示逻辑删除标记，推荐 `0-未删除，1-已删除`
- `created_at`
  表示记录创建时间
- `updated_at`
  表示记录最后修改时间
- `created_by`
  表示创建人标识
- `updated_by`
  表示最后修改人标识

不要把不同语义硬塞进同一高频字段名里，例如用 `type` 同时表示业务分类和流程状态。

### 推荐与不推荐示例

推荐：

- `status`
- `order_status`
- `user_type`
- `source_code`
- `tenant_name`
- `remark`
- `deleted`
- `created_at`
- `updated_at`

不推荐：

- `state`
- `flag`
- `kind`
- `no`
- `desc`
- `memo`
- `is_delete`
- `create_time`
- `update_time`

### 扩展命名规则

如果字段需要更强业务语义，优先采用“业务前缀 + 统一核心词”的方式命名，例如：

- `order_status`
- `biz_type`
- `source_code`
- `customer_name`

不要采用弱语义命名，例如：

- `status1`
- `type2`
- `name3`
- `remark_ext`

不要为了复用老习惯而继续引入近义字段，除非该表需要兼容历史结构。

## 索引设计规范

新增索引时：

- 只为明确查询路径、唯一约束或排序需求建索引
- 不要为了“可能以后会查”滥建索引
- 索引名要能看出用途

推荐命名：

- 主键：
  `pk_表名`
- 唯一索引：
  `uk_表名_字段`
- 普通索引：
  `idx_表名_字段`

联合索引时：

- 按最常用查询条件顺序设计
- 在文档里说明索引服务于哪类查询

### 索引评审项

新增或修改索引前，至少确认：

- 这个索引服务于哪条查询或哪类接口
- 是过滤、排序、唯一约束还是关联查询需求
- 是否已有重复或近似索引
- 是否会影响写入性能
- 联合索引字段顺序是否与主要查询条件一致
- 是否真的需要唯一约束

如果无法明确回答“这个索引服务于哪类查询”，默认不要新增。

## 新增表规范

新增表时至少明确：

- 表用途
- 核心字段
- 主键策略
- 逻辑关联字段
- 状态字段
- 是否需要公共审计字段
- 索引方案

并在业务留痕文档中记录：

- 新增了哪张表
- 这张表服务于哪个业务
- 表之间逻辑关联关系是什么
- 建了哪些索引

## 修改表和字段规范

修改已有表时，要记录动作类型：

- 新增字段
- 修改字段类型
- 修改字段长度
- 修改字段注释
- 新增索引
- 删除索引
- 调整逻辑关联

如果改动可能影响兼容性，还要写明：

- 影响哪些 SQL
- 影响哪些接口
- 是否需要数据回填
- 是否需要兼容旧值

### 历史兼容与演进要求

以下类型的改动，默认视为兼容性敏感变更：

- 修改字段类型
- 缩短字段长度
- 字段拆分
- 字段重命名
- 删除字段
- 调整状态值语义

遇到这类改动时，需要在留痕文档中额外写清：

- 旧结构是什么
- 新结构是什么
- 是否需要数据回填
- 数据如何迁移
- 旧代码或旧 SQL 是否需要兼容期
- 兼容期结束后哪些内容可以清理

如果当前阶段只能先兼容旧结构，也要记录临时方案，不要只在实现里隐式处理。

## SQL 与代码联动规则

如果改动涉及表结构，必须同步检查：

- `code/backend/aldemo/src/main/resources/application.yaml`
- `code/backend/aldemo/src/main/resources/application-mysql.yaml`
- `code/backend/aldemo/src/main/resources/application-oracle.yaml`
- `code/backend/aldemo/src/main/resources/application-postgresql.yaml`
- `db/*/schema.sql`
- `db/*/data.sql`
- `resources/mapper/*.xml`
- repository 查询语句
- DO / DTO / response 字段映射
- 初始化测试数据

不要只改表结构，不回头检查 SQL 和对象映射。

### SQL 生成要求

涉及数据库变更时，SQL 生成至少满足以下要求：

- 先判断当前项目实际使用的数据库类型
- DDL、数据初始化 SQL、数据修复 SQL、兼容迁移 SQL，都按当前数据库方言生成
- DataSQL 文档中的 SQL 代码块，也要按当前数据库方言生成
- 如果当前工程已经维护多数据库脚本目录，除了更新当前目标数据库脚本，也要检查其他数据库目录是否需要同步更新
- 如果本次只更新当前数据库脚本，必须在留痕文档中说明哪些数据库脚本暂未同步

示例理解：

- 当前 profile 是 `dev,mysql`
  留痕中的 SQL 使用 MySQL 语法，表名字段名用小写
- 当前 profile 是 `dev,oracle`
  留痕中的 SQL 使用 Oracle 语法，表名字段名用大写
- 当前 profile 是 `test,postgresql`
  留痕中的 SQL 使用 PostgreSQL 语法，表名字段名用小写

## DataSQL 文档要求

### 汇总清单

`业务变更汇总清单.md` 至少记录：

- 文档头
  - 统计范围
  - 目标数据库类型
  - 数据库判断依据
  - 对应 profile / 配置
  - 文档维护时间
- 汇总概览
  - 业务目录数量
  - 已有真实业务明细数量
  - 模板占位业务数量
  - 涉及表总数
  - 最近一次变更时间
  - 待补或待迁移说明
- 业务清单
  - 业务名称
  - 对应需求模块和模块编码
  - 功能点摘要
  - 目标数据库
  - 涉及表数量
  - 涉及表
  - 最近变更时间
  - 最近变更动作
  - 当前状态
  - 对应明细文档
- 变更索引
  - 一条关键变更一行
  - 记录变更编号、变更时间、时段标签、业务名称、表名、变更动作、变更摘要、对应明细文档
- 待跟进事项
  - 待补明细
  - 待迁移旧格式文档
  - 待同步其他数据库脚本说明

### 业务明细

每个业务目录下的 `表设计与变更记录.md` 至少记录：

- 文档头
  - 业务名称
  - 对应需求模块
  - 模块编码
  - 功能点名称
  - 目标数据库类型
  - 数据库判断依据
  - 对应 profile / 配置
  - 文档维护时间
- 业务涉及表总览
  - 列出该业务当前涉及的全部表
  - 标明每张表的首次创建时间
  - 标明每张表的当前状态和维护状态
- 变更流水总览
  - 一条变更一行
  - 记录变更编号、变更时间、时段标签、表名、变更动作、变更摘要、影响对象、SQL锚点
- 单表详细变更记录
  - 每张表一个独立章节
  - 每章至少包含表基础信息、当前字段清单、当前索引清单、变更历史、SQL脚本明细
- 附加说明
  - 其他数据库脚本同步情况
  - 受影响代码或 SQL
  - 风险与兼容性说明
  - 后续清理项

其中 SQL 代码块至少要覆盖：

- 建表 SQL
- 字段或索引调整 DDL
- 注释 SQL
- 需要时补充数据回填 / 兼容迁移 SQL

### 时间粒度要求

数据库变更留痕中的时间不要只写“上午”或“下午”。

固定要求：

- `变更时间` 使用精确时间：`YYYY-MM-DD HH:mm`
- `时段标签` 作为补充标签，固定使用：
  - `凌晨`
  - `早上`
  - `上午`
  - `中午`
  - `下午`
  - `晚上`
  - `夜间`

推荐做法：

- 同时写精确时间和时段标签
- 文档头中的 `文档维护时间` 也尽量写到分钟

不要只保留模糊时段，不写精确时间。

### 变更动作建议枚举

为了避免多人记录时写出不同说法，推荐优先使用以下动作名：

- `创建表`
- `新增字段`
- `修改字段`
- `删除字段`
- `新增索引`
- `删除索引`
- `调整注释`
- `数据回填`
- `兼容迁移`

如果确实需要扩展动作名，也要保证语义清晰且可归类。

如果本次没有某类 SQL，也要明确写：

```sql
-- 本次无
```

## 验证要求

完成表相关改动后，至少做这些检查：

- 当前数据库类型是否判断正确
- DataSQL 业务目录名是否来自 `docs/需求/模块总表.md`
- 如存在需求模块，`docs/需求/模块/<模块名>/数据库留痕索引.md` 是否已引用本次 DataSQL 变更
- 汇总清单是否能快速看出当前有哪些业务目录和真实业务明细
- 汇总清单中的最近变更时间和最近变更动作是否已刷新
- 汇总清单中的变更索引是否能反向定位到对应业务明细
- 文档是否先给出业务涉及表总览
- 变更流水是否按时间倒序
- 变更时间是否精确到分钟
- 时段标签是否补充完整
- 字段命名是否清晰
- 字段注释是否完整
- 逻辑关联是否写明目标表和字段
- 是否误用了数据库主外键约束
- 索引是否有明确用途
- 单表详细记录是否能独立看懂某张表的当前状态和历史
- DataSQL 明细里是否补了对应 SQL 代码块
- SQL 代码块是否符合当前数据库方言和大小写规范
- DataSQL 汇总和业务明细是否已更新
- 代码和 SQL 是否同步调整

如果改动已经落到应用代码，还应补：

- 启动验证
- SQL 查询验证
- 接口回归验证
- 对应测试说明

## 禁止事项

- 不要使用数据库主外键约束做表关系管理
- 不要新增无注释字段
- 不要新增含糊命名字段
- 不要新增无用途索引
- 不要改了表却不更新 DataSQL 留痕
- 不要只写文字说明却不补 SQL 代码块
- 不要在同一段留痕 SQL 中混写 MySQL、Oracle、PostgreSQL 语法
- 不要只改 SQL 或代码映射而忘记同步表变更说明
