# 多模型交付闭环

## 概述

这个 skill 用来把“规划复核角色负责规划与复核、实现修复角色负责实现与修复”的协作方式，落成一套能执行、能追踪、能反复迭代的半自动流程。

它不直接切换底层模型，也不假装当前工具已经具备自动路由能力。它真正负责的是：

- 先把角色职责分工清楚
- 把当前轮次该由哪个角色工作写进需求包进度文档
- 为下一次切换生成明确的交接提示词
- 到达角色交接点时先停下来，等待用户手动切换后再继续
- 在“实现 -> 复核 -> 修复 -> 再复核”的循环中持续更新状态

## 何时使用

- 用户明确希望把任务拆成“规划复核角色”和“实现修复角色”两类责任
- 当前环境不能自动切换模型，但希望把切换动作规范化
- 需要把“当前责任角色、下一责任角色、验证是否通过、修复建议”记录到 `docs/需求/需求包/`
- 需要让同一个模块在多轮实现与修复中保持清晰的责任交接
- 需要为每次切换输出统一格式的交接包

## 不适用场景

- 全程只打算用一个模型完成任务
- 当前任务只是单点小修复，不值得建立交接闭环
- 当前环境已经有成熟的外层编排器，能自动路由模型并维护状态；此时该 skill 只作为参考，不应重复维护两套流程

## 前置条件

1. 优先先使用 `requirement-implementation-tracking`
   - 先完成需求拆分
   - 先生成 `模块总表.md`
   - 先生成需求包计划与实现进度
2. 如果还没有需求包文档，不先进入多模型交付闭环
3. 涉及数据库结构或 SQL 时，同时遵守 `database-schema-standard`

## 角色职责分工

### 规划复核角色

- 读取需求和原型
- 生成需求包计划
- 拆模块、定步骤、补验收口径
- 做实现后复核
- 记录未通过原因、风险和修复建议
- 在通过后完成收尾检查

### 实现修复角色

- 按已定义的步骤实现代码
- 优先处理窄而明确的实现任务
- 按规划复核角色给出的修复项做定向回改
- 返回本轮修改文件、验证动作和遗留问题

## 角色与工具分离规则

- `当前责任角色` 与 `下一责任角色` 只写角色名，不写具体模型名
- 统一使用两个角色名：
  - `规划复核角色`
  - `实现修复角色`
- 具体使用什么模型、客户端或外部工具，写在 `当前执行工具`
- 如果需要补充更细的环境信息，也放在 `当前执行工具` 或交接包正文中，不把具体模型名写回角色字段
- `agents/openai.yaml` 仅作为当前平台的 skill 展示元数据，不代表把 `openai` 写入责任角色字段；需求包进度仍只记录上面的两个角色名

## 标准流程

1. 建立计划阶段
   - 用 `requirement-implementation-tracking` 先生成需求包
   - 在 `实现计划.md` 中补模块步骤、验收口径和目录映射
   - 如果本次要走多角色协作，在计划中补“角色协作策略（如适用）”
2. 启动交接阶段
   - 在 `实现进度.md` 中写清当前阶段、当前责任角色、当前执行工具和下一责任角色
   - 由当前角色产出下一轮交给对侧角色的执行提示词
3. 实现修复角色实现阶段
   - 实现修复角色按模块和步骤实现代码
   - 完成后把结果回写为“待规划复核角色复核”
   - 记录本轮修改文件、执行过的验证和未解决问题
   - 到达交接点后立即停止当前轮，不继续代替规划复核角色做复核
4. 规划复核角色复核阶段
   - 对照需求包计划、模块记录、代码目录、测试结果和留痕要求做复核
   - 如果通过，更新为“验证通过待收尾”或“已完成”
   - 如果不通过，明确记录问题说明和修复建议，并把下一责任角色切回实现修复角色
   - 到达交接点后立即停止当前轮，不继续代替实现修复角色做修复
5. 修复回环阶段
   - 实现修复角色按修复建议继续修改
   - 再次交回规划复核角色复核
   - 循环直到通过

## 停机点规则

只要出现以下任一情况，当前角色必须先停下来，等待用户手动切换角色后再继续：

1. `规划复核角色` 已完成规划，下一责任角色切到 `实现修复角色`
2. `实现修复角色` 已完成实现，下一责任角色切到 `规划复核角色`
3. `规划复核角色` 复核未通过，下一责任角色切回 `实现修复角色`

执行要求：

1. 先更新 `实现进度.md`
2. 再输出一段固定格式的“角色切换提示”
3. 当前轮到此结束，不继续执行下一责任角色的工作
4. 等用户手动切换角色并回来后，再从新的责任角色继续

不要出现“已经提示切换角色，但当前角色又继续把下一步也做了”的情况。

## 文档落点要求

多模型协作至少要同步更新以下文档：

- `docs/需求/需求包/<需求包>/实现计划.md`
- `docs/需求/需求包/<需求包>/实现进度.md`
- 如有需要，对应 `docs/需求/模块/<模块中文名>/需求实现记录.md`

重点是 `实现进度.md`。其中至少要记录：

- 当前阶段
- 当前状态
- 当前责任角色
- 当前执行工具
- 下一责任角色
- 最近复核轮次
- 最近复核结论
- 验证结果
- 问题说明或修复建议
- 多轮复核记录表

详细字段和阶段说明见：

- `references/state-machine.md`
- `references/prompt-templates.md`

## 标准交接包

每次切换前，统一输出以下交接包，不要自由发挥字段：

- 当前需求包
- 当前模块
- 当前步骤编号
- 当前阶段
- 当前责任角色
- 下一责任角色
- 当前执行工具
- 本轮目标
- 验收口径
- 关联文件/目录
- 已完成内容
- 未完成内容
- 风险或阻塞
- 建议下一动作

## 交接规则

每次角色切换前，至少交接以下内容：

- 当前需求包
- 当前模块与步骤编号
- 本轮目标
- 验收口径
- 关联文件
- 已完成内容
- 未完成内容
- 风险或阻塞

如果当前工具不能自动切换角色，就明确告诉用户：

- 下一步应切到哪个角色
- 下一步建议使用哪个工具
- 可以直接复制的提示词是什么
- 当前轮到此暂停，等待用户切换后再继续

不要在没有真实编排能力的前提下声称“已自动切换角色”。

## 复核重点

规划复核角色复核时，至少检查：

- 是否符合 `实现计划.md` 中的功能点和步骤范围
- 是否落到了正确的后端、前端、测试或 DataSQL 目录
- 是否补了必要验证，或说明未验证原因
- 是否补了需求、变更记录和数据库留痕
- 是否仍存在偏差、遗漏或行为回归

## 复核记录要求

每一轮规划复核角色复核后，都要在 `实现进度.md` 中至少同步两处：

1. 更新“分步骤进度”中的：
   - 最近复核轮次
   - 最近复核结论
   - 是否允许进入下一步
   - 问题说明或修复建议
2. 在“复核记录”表中追加一行，记录本轮：
   - 复核轮次
   - 复核范围
   - 需求符合度
   - 目录落位
   - 验证执行
   - 留痕完整性
   - 回归风险
   - 复核结论
   - 问题级别
   - 修复要求
   - 下一责任角色

如果是多轮复核，不覆盖旧记录，只追加新行。

## 完成定义

只有同时满足以下条件，当前模块或步骤才算通过：

1. 实现结果满足本轮步骤目标
2. 规划复核角色复核通过
3. 验证结果已记录
4. 下一责任角色为空，或状态已变为 `已完成`
5. 需求记录、变更记录和数据库留痕在适用场景下已补齐

## 常见错误

1. 把这个 skill 当成自动切角色工具，而不是半自动协作规程
2. 只有口头说“切回复核看一下”，但没有在进度文档里记录责任切换
3. 实现修复角色做完实现后，没有明确告诉规划复核角色该复核什么
4. 规划复核角色复核只看代码，不看需求包计划、目录落点、测试和留痕
5. 修复回环做了很多轮，但进度文档没有体现每一轮的问题和状态变化
6. 明明已经到切换点了，当前角色却没有停下来等待用户手动切换
