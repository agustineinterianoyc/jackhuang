# 需求拆分与实现计划

## 概述

这个 skill 用来把“已确认的设计输入”变成可执行、可追踪、可和代码目录对齐的开发计划。

它的核心不是单独写某个模块文档，而是在设计基线已经明确或至少主方案已确认的前提下，建立同一套执行事实源：

- `docs/需求/模块总表.md` 记录项目级模块名称、模块编码和对应目录
- `docs/需求/需求包/<需求包>/` 记录本次需求包的整体实现计划
- `docs/需求/需求包/<需求包>/接口清单.md` 记录前后端联动接口契约和联调状态
- `docs/需求/模块/<模块名>/` 记录模块长期演进、实现调整和 DataSQL 索引
- `docs/需求/原始需求/<批次>/批次说明.md` 记录本次输入批次的判定锚点

后续后端代码目录、测试目录、Mapper XML 目录、DataSQL 业务目录，都应优先引用 `模块总表.md` 中的模块编码和模块名称。
需求包计划应优先按业务能力做纵向闭环拆分，把前端、后端、接口、数据库、测试和文档放进同一步骤里追踪；确实只能单独处理的前端或后端事项，再作为独立步骤标注影响面。
当某个步骤准备进入正式开发时，应继续把该步骤细化成“步骤实现明细”。这个明细的目标不是无限细拆，而是细化到 AI 可以直接开发、无需再次追问方向性问题的粒度。
这里的“需求包”定位为执行包，不负责替代设计定稿；如果设计方案尚未稳定，应先回到 `design-doc-generation` 补齐或修订设计文档，再继续执行拆分。

## 何时使用

- 已经存在五份设计文档，或至少已完成主方案评审，需要把设计基线展开成需求包
- 需要根据 `docs/需求/原始需求/<批次>/`、`docs/原型/<批次>/` 和设计文档拆分业务模块
- 需要为一批需求、一个版本或一次迭代建立执行级实现计划
- 需要记录“每个模块要实现什么、按什么步骤做、当前做到哪一步”
- 需要把前端页面、后端接口、数据库变更和联调验证合并成同一份实现计划
- 需要为前后端联动需求建立接口清单并追踪接口状态
- 需要为后端业务代码确定模块目录名，例如 `部门管理 = dept`
- 需要让需求模块、后端代码目录、测试目录和 `code/backend/DataSQL/` 目录保持一致
- 需要复核跨期需求是否复用已有模块，避免重复创建相近模块

## 不适用场景

- 单点小修复，且不涉及需求拆分、模块命名或实现计划
- 只修改已有模块中的一小段实现，且已有需求包计划和模块记录足够清楚
- 纯数据库结构调整且不涉及需求模块规划；此时直接使用 `database-schema-standard`
- 设计方案、接口策略、数据库结构或状态流转仍明显未定；此时应先使用 `design-doc-generation` 产出/修订设计文档并组织评审

## 在整体流程中的定位

本 skill 是“第二阶段执行入口”，负责把已确认的设计层事实源转成执行层需求包。

推荐整体流程：

1. 先由 `design-doc-generation` 基于项目信息、需求和原型生成五份设计文档
2. 组织人工评审并形成设计基线版或设计变更版
3. 再由本 skill 基于“原型 + 需求 + 五份设计文件”生成需求包
4. 在需求包内继续维护模块拆分、步骤明细、接口状态、进度追踪和模块长期记录

边界要求：

- `design-doc-generation` 负责设计方案表达、设计一致性和评审材料
- 本 skill 负责需求包、执行步骤、模块记录、接口协作与进度追踪
- 如果设计文档和需求包冲突，以最近一次评审通过的设计文档为上游依据，先修正需求包再继续推进

## 启动前最低准入条件

在调用本 skill 前，至少应满足以下条件之一：

1. 五份设计文档已经形成“待实施版”或“最终版”基线
2. 至少核心方案已完成评审，接口策略、数据库策略、状态流转和权限边界已基本稳定
3. 属于历史需求补需求包，但已经有足够稳定的设计文档或实现对齐文档可引用

如果以下任一情况仍未明确，默认不要继续产出高置信度需求包，而应先回到 `design-doc-generation`：

- 接口是新增、复用还是扩展尚未定
- 关键状态流转尚未定
- 数据库是扩字段、加新表还是只改逻辑尚未定
- 权限控制边界尚未定
- 变更版究竟以哪个设计版本为准尚未定

## 核心概念

### 项目模块总表

`docs/需求/模块总表.md` 是模块命名的唯一事实源。

它至少记录：

- 模块中文名
- 模块编码，例如 `dept`
- 后端目录名
- DataSQL 业务目录名
- 主要需求包
- 当前状态

新增业务模块前，先查模块总表。能复用已有模块时，继续使用原模块编码，不要因为新需求换一个近义名称。

### 需求包

需求包表示“本次输入的一批需求、一个版本或一次迭代”，不是互相割裂的阶段目录。

第二次需求如果继续改同一个模块，应在新的需求包计划中引用已有模块编码，并在模块目录中追加记录。

推荐目录：

```text
docs/需求/需求包/<YYYY-MM-需求包名称>/
├── README.md
├── 实现计划.md
├── 实现进度.md
└── 接口清单.md
```

`接口清单.md` 是需求包级协作文档，不替代后端代码、Swagger/OpenAPI 或项目既有接口文档体系。涉及前后端联动时必须维护；纯后端、纯前端或纯文档需求可以不创建，但需要在 `README.md` 或 `实现计划.md` 中说明原因。

### 模块目录

模块目录记录该业务模块的长期演进。

推荐目录：

```text
docs/需求/模块/<模块中文名>/
├── README.md
├── 需求实现记录.md
├── 需求实现优化调整记录.md
└── 数据库留痕索引.md
```

`数据库留痕索引.md` 只放 DataSQL 链接、涉及表摘要和变更编号索引，不重复维护完整 DDL 或字段清单。

## 标准流程

1. 先确认本次执行所依赖的设计版本：
   - 当前对应的设计基线版 / 设计变更版名称
   - 文档状态是否已达到“可用于执行拆分”
   - 若设计版本不明确，先补齐版本信息，不直接开始拆步骤
2. 读取输入资料：
   - `docs/需求/原始需求/<批次>/` 下的需求文件
   - `docs/需求/原始需求/<批次>/批次说明.md`
   - `docs/原型/<批次>/` 下的原型说明和页面
   - 已评审的《概要设计说明书》《详细设计说明书》《数据库设计说明书》《接口清单》《需求实现计划》
   - 如果当前环境安装并触发全局 `using-superpowers` skill，可同时参考 `docs/superpowers/` 下已有 specs / plans；否则不要要求创建或维护该目录
   - 已有 `docs/需求/模块总表.md`
   - 已有 `code/backend/DataSQL/业务变更汇总清单.md`
3. 计划前澄清：
   - 先记录需求包目标、成功标准、受众或使用者
   - 明确本次范围内、本次范围外、已知约束、默认假设和待确认问题
   - 能从需求、原型、设计文档、代码或历史文档确认的问题先自行确认；只把无法判断且会影响实现方向的问题列为待确认
   - 待确认问题不阻塞计划时，应写明采用的默认假设，并在后续实现进度中持续追踪
   - 如果发现关键设计仍未定，应先停止继续细化执行步骤，回到 `design-doc-generation` 修订设计文档

### 待确认问题分级

为了避免“什么都停下来问”或“什么都自己猜”，待确认问题建议分为三类：

- A 类：必须先确认，不能靠默认假设硬推
  - 会直接影响业务方向、状态机、权限边界、接口策略或历史兼容策略
  - 典型例子：
    - 是新增接口还是扩展旧接口
    - 状态合并是显示层合并还是编码层合并
    - 权限控制是仅前端显隐还是后端也必须强校验
    - 历史数据是否必须补迁移脚本
- B 类：可先按默认假设推进拆分，但必须显式写入文档持续跟踪
  - 不影响本轮模块拆分和总体步骤顺序，但会影响实现细节
  - 典型例子：
    - 是否需要补操作来源字段
    - 导出字段顺序是否沿用旧版
    - 列表默认排序口径是否调整
- C 类：实现时再确认即可，不阻塞计划和步骤细化
  - 更偏展示、文案、微交互或非关键默认值
  - 典型例子：
    - 按钮文案是否用“保存并提交”还是“编辑并提交”
    - 空态提示语
    - 非关键列宽、默认展开态

默认规则：

- A 类问题未确认前，不要把该部分标记为“可正式开发”
- B 类问题可以继续拆计划，但必须在 `README.md`、`实现计划.md` 或 `实现进度.md` 中保留追踪点
- C 类问题无需在计划阶段过度展开，避免噪音
4. 先做变更类型判定：
   - 结合 `批次说明.md`、现有模块总表、历史需求包、设计基线和原型输入
   - 先输出“本次判定类型、判定依据、对需求包的动作、对模块总表的动作”
   - 判定类型统一使用：`小改动`、`阶段性变更`、`新需求包`
5. 拆分业务模块：
   - 按业务对象、业务流程、权限边界、数据表归属和页面菜单判断模块
   - 优先复用已有模块，不因为同义词重复建模块
   - 给新模块生成简短英文模块编码，例如 `dept`、`dict`、`order`
6. 更新模块总表：
   - 新模块先登记模块总表
   - 已有模块补充新需求包引用、状态和说明
7. 建立需求包计划：
   - 写 `README.md`
   - 写 `实现计划.md`
   - 写 `实现进度.md`
   - 涉及前后端联动时写 `接口清单.md`
   - 需求包中的步骤、接口、数据库动作和验证口径，应尽量引用已确认的设计文档，而不是重新发明一套口径
   - 步骤优先按业务闭环纵向拆分，不要先拆成互相隔离的“前端计划”和“后端计划”
   - 每个步骤必须标注影响面，例如 `[前端]`、`[后端]`、`[前后端]`、`[数据库]`、`[接口]`、`[测试]`、`[文档]`
   - 涉及接口的步骤必须关联接口编号，例如 `API-001`
   - 如果当前任务明确采用多模型协作，再由 `multi-model-delivery-loop` 补角色分工、交接提示词和责任切换状态
8. 建立或更新模块目录：
   - 写模块 `README.md`
   - 写 `需求实现记录.md`
   - 写 `需求实现优化调整记录.md`
   - 如涉及数据库，写 `数据库留痕索引.md`
9. 对齐代码与数据库目录：
   - 后端业务代码按模块编码建立子目录
   - DataSQL 业务目录优先使用模块总表中的 DataSQL 目录名
   - 需求模块只引用 DataSQL，不重复写完整 SQL
10. 收尾复核：
   - 复核需求覆盖、页面覆盖、接口覆盖、数据库 / DataSQL 覆盖、验证执行和留痕完整性
   - 前后端联动需求必须确认 `接口清单.md` 中相关接口达到约定状态，至少能看出后端实现、前端接入和联调进展
   - 未完成或无法验证的项目必须写入 `实现进度.md` 的问题说明或风险待办

## 模块编码规则

模块编码用于后端包目录、Mapper XML 目录、测试目录和部分变更编号前缀。

规则：

- 使用小写英文、数字和短横线，Java 包目录优先使用小写英文单词
- 尽量短，通常 1 到 2 个业务词
- 与业务中文名稳定对应，例如 `部门管理 = dept`
- 同一个模块跨需求包保持不变
- 不确定时优先选择业务对象名，而不是页面动作名

示例（以下为通用示意，实际模块名以项目业务为准）：

| 模块中文名 | 模块编码 | 后端目录名 | 数据库留痕目录名 |
| --- | --- | --- | --- |
| 部门管理 | `dept` | `dept` | `部门管理` |
| 字典管理 | `dict` | `dict` | `字典管理` |
| 订单管理 | `order` | `order` | `订单管理` |

## 后端目录对齐

业务应用模块中的新增业务代码，按模块编码建立子目录。

示例：`部门管理 = dept`

```text
controller/dept/
service/dept/
service/dept/impl/
repository/dept/
repository/dept/impl/
mapper/dept/
model/request/dept/
model/response/dept/
model/vo/dept/
model/dataobject/dept/
resources/mapper/dept/
src/test/java/.../app/dept/
src/test/resources/test-report/dept/
```

Maven 模块边界以项目 `AGENTS.md` 或 Maven POM 定义为准，不在此处写死。典型分层：

- 公共契约 / API 定义模块
- 基础设施 / 通用工具模块
- 数据访问 / 通用数据能力模块
- 具体业务应用模块

使用时应先读取项目的 `code/backend/AGENTS.md` 或 `pom.xml`，确认实际的模块划分和依赖方向，再按模块编码在对应业务模块下建立子目录。

## 与 DataSQL 的关系

DataSQL 是数据库结构、SQL、字段、索引和变更流水的正式来源。

需求模块目录只维护索引：

- 对应 DataSQL 业务目录
- 涉及表名摘要
- 关键变更编号
- 与需求包或模块计划的关联说明

不要在 `docs/需求/模块/*/数据库留痕索引.md` 中重复完整建表 SQL、字段清单或索引清单。

涉及数据库结构、DDL、Mapper SQL、初始化 SQL 时，必须同时使用 `database-schema-standard`。

## 与接口清单的关系

`接口清单.md` 是需求包级前后端协作清单，用于把实现计划、后端接口和前端接入状态串起来。

规则：

- 只有涉及前后端联动的需求包才必须维护 `接口清单.md`
- 接口编号使用需求包内稳定编号，例如 `API-001`、`API-002`
- `实现计划.md` 中涉及接口的步骤必须填写关联接口编号
- `实现进度.md` 中涉及接口的步骤必须记录接口状态、前端状态、后端状态和联调状态
- `接口清单.md` 只维护协作契约摘要，不重复维护完整 OpenAPI 文档
- 后端代码、Swagger/OpenAPI 或项目既有接口体系仍是正式接口定义来源

推荐状态：

- 待设计
- 待实现
- 后端已实现
- 前端已接入
- 联调通过
- 变更中
- 已废弃

## 与 `docs/superpowers/` 的关系

`docs/superpowers/` 属于全局 `using-superpowers` skill 的可选记录层，不是本项目内置强制目录。

规则：

- 当前环境安装并触发 `using-superpowers`，或用户明确要求使用 superpowers 流程时，可以把 specs / plans 写入 `docs/superpowers/`
- 未安装或未触发 `using-superpowers` 时，不创建、不补齐、不要求维护 `docs/superpowers/`
- 无论是否使用 superpowers，正式需求拆分结果都要落回 `docs/需求/模块总表.md`、`docs/需求/需求包/` 和 `docs/需求/模块/`

## 与 `docs/工作台/` 的关系

`docs/工作台/` 是面向人工阅读的静态总览层，不是正式事实源。

规则：

- 需求、模块、需求包的正式内容仍写在 Markdown 中
- 工作台只消费这些文档中的结构化字段和链接
- 不要反过来把工作台页面当作需求拆分输入或唯一事实源

## 与 `multi-model-delivery-loop` 的关系

`requirement-implementation-tracking` 负责在设计基线已确认后，把需求拆成模块、步骤和需求包计划。

如果用户后续明确采用“规划复核角色规划复核、实现修复角色实现修复”的协作方式，再由 `multi-model-delivery-loop` 负责：

- 在 `实现进度.md` 中维护当前责任角色与下一责任角色
- 生成交接提示词
- 维护复核未通过后的修复回环

不要反过来让 `multi-model-delivery-loop` 替代需求拆分与模块规划。

## 与 `design-doc-generation` 的关系

`design-doc-generation` 是本 skill 的上游。

规则：

- 新需求默认先产出五份设计文档，再生成需求包
- 需求变更默认先修订五份设计文档并形成设计变更版，再生成变更需求包
- 如果执行中发现设计文档缺失、冲突或明显不足以支撑拆分，应暂停继续细化步骤，先回到 `design-doc-generation`
- 本 skill 生成的 `README.md`、`实现计划.md`、`实现进度.md`、`接口清单.md` 属于执行层产物，不替代《概要设计说明书》《详细设计说明书》《数据库设计说明书》
- 如果设计层也有《接口清单》或《需求实现计划》，应通过目录、版本和文档头说明清楚区分“设计层”与“执行层”，不要把两者混写成同一份文档


## 变更类型判定规则

- `小改动`
  - 命中已有模块
  - 未引入新的业务主流程或业务对象
  - 默认更新已有模块记录和当前需求包进度，不新建需求包
- `阶段性变更`
  - 仍属于同一业务主题
  - 但形成新的批次、阶段或明显新一轮实现计划
  - 默认新建需求包，复用已有模块编码
- `新需求包`
  - 新增业务域、新菜单域、新流程域，或明显新增模块边界
  - 默认新建需求包；如需新增模块，同时更新模块总表

### 变更类型判定示例

- `小改动`
  - 示例 1：在已有模块列表页增加一个查询条件，接口和状态流转不变
  - 示例 2：在已有审核页补一个导出按钮，仅影响当前需求包中的一个步骤
  - 常见动作：更新已有模块记录、补当前需求包进度，不单独新建需求包
- `阶段性变更`
  - 示例 1：同一业务域进入第二批原型或 V2.x 迭代，需要重新梳理一轮实现计划
  - 示例 2：同一模块追加一批明显成体系的新规则，虽未形成新业务域，但已超出“小修小补”
  - 常见动作：新建需求包，复用原模块编码，并在模块目录追加本轮记录
- `新需求包`
  - 示例 1：新增独立菜单域、独立业务对象和独立主流程
  - 示例 2：新增一个与现有模块边界明显不同的新业务模块，需要单独建立目录、接口和数据库留痕映射
  - 常见动作：新建需求包；如有新模块，同时更新 `模块总表.md`

判定时优先看“是否形成新的业务边界和新的跟踪单元”，不要只看改动行数多少。
执行拆分时，还应确认本次判定与最近一次评审通过的设计文档版本一致；如果设计版本尚未同步，应先补设计版本再生成需求包。

### 步骤实现明细化规则

当 `实现计划.md` 中的某一步准备进入正式开发时，应在该步骤下或旁边补充“步骤实现明细”。

原则：

- 细化目标是让 AI 可以直接开发，不是为了把任务拆到越细越好
- 默认先有“需求包级实现计划”，再对当前准备开发的步骤做二次细化
- 只对复杂步骤、跨前后端步骤、状态/权限/接口口径容易歧义的步骤补实现明细
- 如果某一步已经足够清楚，AI 拿到后可以直接改代码，则不要为了形式继续细拆
- 不要把实现明细写成人工排期式的碎任务清单，除非后续明确要并行分配给多人或多模型

推荐触发时机：

- 某一步涉及多个页面、多个接口或多个状态口径
- 某一步同时影响前端、后端、数据库或 DataSQL
- 某一步存在“扩展旧接口还是新增动作接口”的设计分歧
- 某一步准备立即进入编码或交给 AI 独立实现

### 可正式开发的粒度标准

一条步骤已经达到“可正式开发”标准时，至少满足以下条件：

1. 业务目标单一
   - 该步骤只解决一个主闭环，不混入多个无关目标
2. 影响范围清楚
   - 至少能说明受影响的页面、接口、状态、数据或 SQL
3. 前后端职责清楚
   - 前端做什么、后端做什么、数据库 / 兼容做什么可以分清
4. 验收口径清楚
   - 做完以后如何判断完成、看哪些场景或结果
5. AI 无需再次追问方向性问题
   - 不需要再问“新增接口还是扩展接口”
   - 不需要再问“这是显示层合并还是编码层合并”
   - 不需要再问“前端只隐藏按钮还是后端也要禁止”

只要满足以上条件，就可以直接进入开发；不要求继续细化到字段级、行号级或人工排期级粒度。

### 步骤实现明细推荐结构

单个步骤的实现明细，推荐至少包含：

- 步骤目标
- 影响页面
- 影响接口
- 状态 / 权限 / 只读态口径
- 前端实现要点
- 后端实现要点
- 数据库 / DataSQL / 历史兼容要点
- 主要文件范围（允许写目录、页面、service、controller、request/vo 层级，不强制行号）
- 验证方式
- 验收口径
- 默认假设与待确认问题

推荐写法：

- 优先写“这一条做完会得到什么”
- 优先写“改哪里”和“为什么改”
- 文件范围写到足够让 AI 开工即可，不要求提前精确到每一行
- 对复杂步骤，可以补一个建议开发顺序，例如“先状态基线，再列表页，再详情页，再审核页”

不推荐写法：

- 把一个步骤拆成大量 1 分钟级碎任务，但这些碎任务不会改变实现方向
- 在计划阶段提前写死所有字段、所有行号和所有测试命令，导致文档快速过时
- 只有前端清单或只有后端清单，没有同一业务闭环下的联动说明

### 步骤粒度正反例

- 过粗示例：
  - “完成整个模块前端”
  - “完成全部后端接口”
  - “做完联调”
  - 问题：业务闭环不清楚，无法判断该步是否真正完成
- 过细示例：
  - “新增一个按钮”
  - “改一个枚举值”
  - “改一个 if 判断”
  - 问题：这些是实现动作，不是需求步骤，容易把计划写成人工排期清单
- 合理示例：
  - “完成审核页编辑并提交闭环，包括按钮入口、接口动作、状态控制、权限校验和验证回归”
  - 关键标准：一步对应一个可验收的业务闭环

### 需求包级计划与步骤级明细的关系

- `实现计划.md` 负责给出需求包级、模块级和业务闭环级的总顺序
- “步骤实现明细”负责把当前准备开发的单一步骤补到可执行粒度
- 如果某一步已经满足“可正式开发”标准，可以直接进入编码，不必继续细拆
- 如果后续采用多模型协作，可把“步骤实现明细”作为具体交接输入，而不是重新从原始需求开始解释

### 步骤实现明细示例

以下示例用于说明"什么叫细化到 AI 可以直接开发"，不是要求所有步骤都照抄成同样长度。

> **注意：** 示例中的模块名、页面名、文件路径均为示意，使用时应替换为当前项目的实际名称。文件路径以项目 `code/frontend/AGENTS.md` 和 `code/backend/AGENTS.md` 中的目录约定为准。

示例场景：某模块中，审核页新增"编辑并提交"能力。

```markdown
#### <MODULE>-<STEP-ID> 实现明细

- 步骤目标：
  - 让审核角色在审核详情页中，不仅可以"通过 / 退回"，还可以直接修改明细后执行"编辑并提交"。

- 影响页面：
  - 审核详情页
  - 关联只读回显页（确认提交后回显口径不冲突）

- 影响接口：
  - 审核详情接口
  - 审核动作接口
  - 必要时扩展明细保存 / 提交接口，或新增审核态专用"编辑并提交"动作接口

- 状态 / 权限 / 只读态口径：
  - 仅待审核状态允许"编辑并提交"
  - 已审核通过、已退回、已发布状态只允许查看
  - 前端按钮显隐以后端权限和状态口径为准，不自行猜测

- 前端实现要点：
  - 在审核详情页中区分"审核态"和"只读态"
  - 审核态下允许编辑明细字段
  - 增加"编辑并提交"按钮，并与"通过 / 退回"并列
  - 提交成功后刷新详情和列表状态

- 后端实现要点：
  - 明确"编辑并提交"是复用旧保存/提交能力，还是新增审核动作
  - 保证审核角色修改的是审核上下文中的明细，而不是绕回普通填报入口
  - 留存必要的审核动作和修改痕迹，避免后续无法区分"填报提交"和"审核态修改提交"

- 数据库 / 留痕 / 历史兼容要点：
  - 如果只是复用既有明细表且不新增字段，可不新增 DDL
  - 如果需要区分审核态修改来源、操作人或时间，需评估补字段并同步数据库留痕
  - 历史数据不要求补齐该类痕迹时，要在实现说明中写清兼容策略

- 主要文件范围：
  - 前端：`<前端工程>/src/views/<module>/AuditDetail.vue`
  - 前端类型：`<前端工程>/src/types/<module>.ts`
  - 后端 controller：`controller/<module>/AuditController.java`
  - 后端 service：`service/<module>/impl/AuditServiceImpl.java`
  - 必要时涉及 request / vo / mapper / 数据库留痕目录

- 验证方式：
  - 构造"待审核"任务，验证可以编辑后提交
  - 构造"已通过 / 已退回"任务，验证只能查看不能修改
  - 校验提交后列表状态、详情状态和后续流转不冲突

- 验收口径：
  - 审核角色可以在审核页对待审核任务执行"编辑并提交"
  - 原有"通过 / 退回"路径不被破坏
  - 提交后的回显、状态流转和只读控制一致

- 默认假设与待确认问题：
  - 默认假设：优先扩展现有审核动作，不额外新开完全独立页面
  - 待确认：是否需要单独记录"审核态编辑提交"操作来源字段
```

这个示例的关键点：

- 已经足够让 AI 开发
- 但没有细到字段级、行号级
- 同时覆盖前端、后端、状态、兼容和验证
- 后续如果进入真正编码阶段，AI 仍然需要自己读取相关代码，而不是机械照抄计划

`实现计划.md` 至少包含：

- 对应设计基线版本 / 设计变更版本
- 需求包目标
- 计划前澄清结果，包括成功标准、范围内外、默认假设和待确认问题
- AI 判定结果
- 模块拆分结论
- 模块依赖顺序
- 每个模块要实现的功能点
- 按业务闭环拆分的分步骤实现计划
- 每个步骤的影响面、接口编号、前端任务、后端任务、数据库任务和验证方式
- 前端、后端、数据库、原型和测试影响
- 验收口径

`实现进度.md` 至少包含：

- 模块
- 步骤编号
- 步骤内容
- 影响面
- 接口编号
- 当前状态
- 接口状态、前端状态、后端状态和联调状态

## 常见错误

1. 先写代码目录，再回头随便补模块名，导致文档和代码不一致
2. 新需求继续改已有模块，却新建了近义模块目录
3. 需求文档、后端包目录和 DataSQL 目录各自命名
4. 在需求模块里重复写完整 SQL，和 DataSQL 形成两份事实源
5. 还没形成设计基线，就直接把需求包当成主事实源，导致后续执行与评审口径脱节
6. 只有模块文档，没有需求包整体计划，后续看不出开发顺序和进度
7. 没有提供 `批次说明.md`，让 AI 只能猜本次属于小改动还是新需求包
8. 把前端计划和后端计划完全拆散，导致同一个业务闭环缺少接口和联调追踪
9. 涉及前后端联动但没有维护 `接口清单.md`，后续看不出接口是否实现、接入和联调通过
