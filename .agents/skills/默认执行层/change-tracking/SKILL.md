# 变更记录

## 概述

这个 skill 用来让重要项目变更能被后续人工和 AI 回查。

Git 负责记录“改了什么文件”。
变更记录负责记录“为什么改、影响什么、以后从哪里继续看”。

除非用户明确要求当前轮只做分析、不改任何文件，否则命中记录条件后必须直接落文档，不能只给口头判断。

## 何时使用

当变更命中以下任一情况时使用：

- 需求口径变化
- 架构或目录结构调整
- 公共规范、编码规则、AI 执行规则变化
- 跨模块 Bug 修复
- 变更虽然从局部开始，但后续很可能需要反查决策原因

以下情况通常不使用：

- 纯样式微调
- 无行为变化的小范围格式整理
- 不改变规则含义的错别字修正

以下情况即使只改 1 个文件、只影响单一模块，也应优先记录：

- 生产问题或联调问题的 Bug 修复
- 配置默认值修正、阈值调整、开关变更
- 上传、鉴权、超时、并发、缓存、序列化等运行时行为修复
- 虽然改动很小，但后续很可能有人追问“为什么要这么改”

不要把“改动小”直接等同于“不需要记录”。
只要变更带来了真实行为变化，尤其是 Bug 修复或配置修正，就应至少补对应层级的 `CHANGELOG.md`。

## 记录级别

先选择最近且足够的记录级别：

1. 模块级 `CHANGELOG.md`
2. 项目级 `docs/变更记录/`

使用模块级 `CHANGELOG.md` 的条件：

- 只影响单一前端模块或单一后端模块
- 不改变需求口径
- 不改变架构边界
- 不改变公共规范
- 不跨前后端

典型例子：

- 单服务上传大小限制修复
- 单模块超时参数调整
- 单接口返回映射修正
- 单任务调度配置修正

使用 `docs/变更记录/` 的条件：

- 改变需求口径
- 改变架构或目录结构
- 改变公共规范或执行规则
- 修复跨模块 Bug
- 跨前后端
- 后续很可能需要反查“为什么这样改”

硬性规则：

- 只要同一次任务同时修改了 `code/frontend/` 和 `code/backend/`，无论改动大小，默认按项目级记录处理，更新 `docs/变更记录/`。
- 即使用户最初描述的是“页面显示不对”“浏览器里看一下”“联调时有问题”，只要最终落成前后端联动修复，也不能只停留在模块级 `CHANGELOG.md`。

如果一个变更最初看起来是局部修改，但命中了任一项目级条件，也要升级记录到 `docs/变更记录/`。

## 必备目录

项目级变更目录应保持以下结构：

- `docs/变更记录/README.md`
- `docs/变更记录/CHANGELOG.md`
- `docs/变更记录/需求变更.md`
- `docs/变更记录/架构变更.md`
- `docs/变更记录/规范变更.md`
- `docs/变更记录/bug修复.md`

如果目录不存在，且当前任务触发本 skill，完成前必须先创建。

## 执行动作

触发后按顺序执行：

1. 在宣称完成前，强制判断本次是模块级记录还是项目级记录。
2. 模块级变更：
   - 前端更新 `code/frontend/CHANGELOG.md`
   - 后端更新 `code/backend/CHANGELOG.md`，并在每条记录里标明模块名
3. 项目级变更：更新 `docs/变更记录/CHANGELOG.md` 摘要。
4. 项目级变更：更新对应分类文件的完整记录：
   - `需求变更.md`
   - `架构变更.md`
   - `规范变更.md`
   - `bug修复.md`

如果一个变更跨多个分类，`CHANGELOG.md` 只写一条摘要，相关分类文件分别写完整记录。

如果模块级变更缺少对应 `CHANGELOG.md`，补齐以下固定文件：

- 前端：`code/frontend/CHANGELOG.md`
- 后端：`code/backend/CHANGELOG.md`

## 强制收尾规则

- 只要任务实际产生了变更，就必须在最终回复前完成一次留痕判定。
- 命中记录条件后，直接更新对应文档，不要输出“要我帮你记录吗”“是否需要我补记录”这类话术。
- 最终回复应写“已更新哪个记录文件”，而不是只写“需要记录”或“建议记录”。
- 唯一例外是用户明确要求本轮只做分析、不改文件。

## 必填字段

详细记录至少包含：

- 背景
- 变更内容
- 影响范围
- 涉及文件
- 决策原因
- 风险或兼容性说明

Bug 修复还应补充已知根因。

## 与其他 skill 的关系

- `requirement-implementation-tracking` 负责需求拆分、模块总表、需求包计划和实现进度；如果只是一次新需求包或阶段性需求落地，先维护需求包文档。
- 当需求调整会推翻已确认口径、影响多个模块、改变公共协作规则，或后续需要反查决策原因时，再同步使用本 skill 写入 `docs/变更记录/`。
- `database-schema-standard` 负责数据库结构、Mapper SQL 和 DataSQL 留痕；数据库变更本身必须先按该 skill 留痕。如果同时改变公共数据库规范或跨模块数据关系，再使用本 skill 写项目级记录。
- `backend-development-standard`、前端开发约束或发布脚本规则发生公共规范变化时，使用本 skill 写 `规范变更.md`。

## 模板入口

优先复用本 skill 的模板：

- `.agents/skills/默认执行层/change-tracking/templates/changelog-module-template.md`
- `.agents/skills/默认执行层/change-tracking/templates/global-changelog-entry.md`
- `.agents/skills/默认执行层/change-tracking/templates/category-record-template.md`

模板只提供骨架。落地时应结合本次真实背景、影响范围和涉及文件填写，不要保留占位符。

## 排版要求

- 所有 `CHANGELOG.md` 和 `docs/变更记录/*.md` 按时间倒序排列。
- 文档开头应有清单表格，快速列出日期、类型、模块和标题。
- 模板示例放在真实记录之后，不能挡在文档开头。

## 快速映射

| 变更类型 | 更新文件 |
| --- | --- |
| 需求变更 | `需求变更.md` |
| 架构或目录结构调整 | `架构变更.md` |
| 规范或执行规则调整 | `规范变更.md` |
| Bug 修复 | `bug修复.md` |

## 收尾检查

在宣称完成前检查：

- 是否修复了 Bug
- 是否修正了配置导致的运行时行为
- 是否改变了需求口径
- 是否改变了目录或模块边界
- 是否改变了公共规范或执行规则
- 局部变更是否已经影响多个模块
- 局部变更是否已经跨前后端
- 是否同一次任务同时修改了 `code/frontend/` 和 `code/backend/`
- 是否已经完成留痕判定，而不是只在脑中判断
- 如果命中记录条件，是否已经实际更新文档，而不是只输出“需要记录”
- 是否快要说“完成”，但还没有任何 `CHANGELOG.md` 或 `docs/变更记录/` 更新

## 规则

不要把 Git 历史当成变更记录的替代品。

Git 回答：改了什么。
变更记录回答：为什么改、影响什么、后续从哪里继续。
