# 设计文档生成

## 定位

把“需求 + 原型 + 工程事实”整理成可评审、可约束后续实现的设计文档。文档需要同时产出两类内容：

- 给人评审的设计结论、边界、规则、风险和待确认点
- 给后续实现使用的稳定事实、约束、接口、数据和验收口径

## 何时使用

- 新需求需要先形成设计说明，再进入开发
- 需求变更后需要同步调整设计文档
- 已有实现但缺少设计说明，需要基于代码、接口、数据库反向整理
- 需要把原型、需求、接口、数据库约束整理成可人工评审的材料
- 需要给后续开发提供稳定上下文，避免只凭口头需求直接写代码

## 文档集合

默认生成四份文档：

1. 《设计说明书》
2. 《数据库设计说明书》
3. 《接口清单》
4. 《需求实现计划》

如果任务只需要其中一部分，只生成相关文档，不要为了凑齐文档而制造空内容。

模板入口：

- `templates/设计说明书.md`
- `templates/数据库设计说明书.md`
- `templates/接口清单.md`
- `templates/需求实现计划.md`

## 生成要求

- 优先写设计结论、边界、规则、风险和待确认事项
- 不生成空泛套话、审批字段、签核字段或没人维护的流程信息
- 与当前需求无关的安全、部署、灾备、组件资源内容不要补充
- 如果用户明确要求正式归档格式，再按用户要求补充流程字段

## 事实源优先级

生成文档时按以下优先级判断事实可信度：

1. 项目规范与当前目录约定
2. 正式需求文档 / 原型文档
3. 已存在的设计文档
4. 实际代码实现，如 controller、service、request、response、mapper
5. 数据库结构与数据库留痕，如 DDL、迁移脚本、表设计记录
6. 前端调用、接口文档、OpenAPI、Swagger
7. 变更记录、历史说明、口头补充

规则：

- 有明确事实源时，不要用想象补设计
- 需求与实现冲突时，要同时写出“需求口径”和“实现现状”
- 无法确认的内容进入“待确认事项”，不要伪装成已定方案
- 如果事实源不足，应先说明缺口，再生成可确认部分

## 生成流程

1. 判断本次是新需求设计、变更设计、开发中补齐，还是开发后反向整理
2. 确认需要生成哪几份文档
3. 收集需求、原型、历史设计、接口、数据库、代码事实
4. 先提炼设计结论，再填充细节表格
5. 对无法确认的点标记为待确认或风险
6. 在文档末尾沉淀实现约束类摘要章节
7. 做跨文档一致性检查

## 四类文档规则

### 1. 设计说明书

用途：合并原概要设计和详细设计，作为人工评审的主文档。

应包含：

- 设计目标和结论
- 范围与边界
- 角色、场景、模块划分
- 业务流程、异常流、状态流转
- 页面交互、字段校验、权限规则
- 前后端实现方案概要
- 验证与验收口径
- 风险与待确认事项
- 开发约束摘要

模板：`templates/设计说明书.md`

### 2. 数据库设计说明书

用途：说明数据库结构、数据关系、状态枚举、迁移和兼容策略。

应包含：

- 表清单和表用途
- 字段说明
- 主键、唯一键、索引、约束
- 表间逻辑关系
- 状态字段和枚举
- 数据迁移与历史兼容
- SQL / 留痕目录映射
- 数据库实现约束

模板：`templates/数据库设计说明书.md`

### 3. 接口清单

用途：沉淀前后端协作所需的接口契约。

应包含：

- 接口编号、接口名称、业务场景
- 请求路径、方法、调用入口
- 请求参数、响应摘要
- 权限要求、状态要求、异常说明
- 新增、调整、延用、废弃接口的区分
- 接口实现约束

模板：`templates/接口清单.md`

### 4. 需求实现计划

用途：从设计视角说明推荐实现路径，不做执行级进度管理。

应包含：

- 实施目标和成功标准
- 范围内 / 范围外
- 模块拆分结论
- 计划前澄清
- 分阶段实现路径
- 里程碑与依赖
- 验证方式和验收口径
- 开发顺序与验证约束

模板：`templates/需求实现计划.md`

## 一致性检查

生成完成后至少检查：

- 四份文档中的模块名称一致
- 接口编号、接口名称、调用场景一致
- 状态流转在设计说明、接口、数据库中不冲突
- 表名、字段名、枚举值与数据库事实源一致
- 实现计划中的阶段路径能映射到设计说明、接口清单和数据库设计
- 所有无法确认的内容已进入待确认事项
- 实现约束类摘要只包含可约束实现的事实和规则

## 交付要求

完成时说明：

1. 生成了哪些文档
2. 每份文档主要依据哪些事实源
3. 哪些内容仍需人工确认
4. 哪些设计结论会直接约束后续实现
