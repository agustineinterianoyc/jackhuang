## 2026-05-19 脚手架文档架构收敛为“根路由 + 工程事实 + 规则真源 + 业务事实 + skill 逻辑分层”

- 背景：
  现有脚手架已经具备较完整的 AI 治理能力，但根 `AGENTS.md`、流程文档、需求目录说明、变更记录目录说明和多个 skill 之间存在明显的职责重叠。日常开发时，AI 很容易把本应按需触发的规则和说明一起带进上下文，导致入口过胖、阅读链路过长。

- 变更内容：
  将流程文档并入 `docs/规范/AI开发SOP.md`，并在 `docs/` 下正式形成“规范 / 需求 / 变更记录 / 原型 / 工作台 / 原型站点”分层。根 `AGENTS.md` 改为超薄任务路由页，只负责分流与 skill 分层；`code/frontend/AGENTS.md`、`code/backend/AGENTS.md` 收敛为工程事实入口；`docs/需求/readme.md` 和 `docs/变更记录/README.md` 退回目录职责说明；`.agents/skills/` 物理分层为“默认执行层 / 条件触发层 / 人工触发层”，不再只停留在逻辑索引层。

- 影响范围：
  影响后续所有进入仓库后的默认阅读顺序和规则定位方式。今后默认上下文优先读取根路由、工程级入口与命中规则，而不是把需求说明、变更说明和专项 skill 一次性全部展开。

- 涉及文件：
  `AGENTS.md`
  `docs/规范/AI开发SOP.md`
  `docs/规范/`
  `docs/需求/readme.md`
  `docs/变更记录/README.md`
  `code/frontend/AGENTS.md`
  `code/backend/AGENTS.md`
  `.agents/skills/README.md`
  `.agents/skills/默认执行层/`
  `.agents/skills/条件触发层/`
  `.agents/skills/人工触发层/`
  `docs/工作台/`
  `docs/原型站点/`
  `docs/变更记录/CHANGELOG.md`
  `docs/变更记录/架构变更.md`

- 决策原因：
  这次重构一次性把“层次、职责和关键目录物理位置”一起调整到最终形态，避免后续再经历第二轮路径迁移。通过同步更新 `project-init`、原型 skill、工作台脚本和目录说明，可以在一次迁移中把默认上下文和物理目录都收口到位。

- 风险或兼容性：
  当前生效目录已经迁移到 `docs/规范/AI开发SOP.md`、`docs/工作台/` 和 `docs/原型站点/`。历史变更记录中的旧路径说明保留为历史语境，但运行链路上的活文档、活脚本和活 skill 都必须按新路径执行。

## 2026-05-14 清理脚手架演示业务模块并补齐空目录占位

- 背景：
  当前仓库作为脚手架继续使用时，不应默认携带演示接口、演示页面、示例 SQL、示例需求包和示例 DataSQL 目录；但直接删除后又会导致部分标准目录变成空目录，后续新增真实业务时缺少稳定落点。

- 变更内容：
  删除前后端演示业务链路、演示初始化 SQL、示例需求批次、示例原型批次、示例需求包、示例模块记录和示例 DataSQL 目录。对被清空但仍属于工程骨架的目录补 `.gitkeep`，并将首页、工作台数据、模块总表和 DataSQL 汇总清单调整为空骨架状态。

- 影响范围：
  影响 `code/frontend/`、`code/backend/ai-training-project/`、`code/backend/DataSQL/`、`docs/需求/`、`docs/原型/` 和 `docs/workbench/`。后续真实业务开发需要先登记模块与需求包，再新增前后端实现和数据库留痕。

- 涉及文件：
  `code/frontend/src/router/index.ts`
  `code/frontend/src/views/index.vue`
  `code/backend/ai-training-project/src/main/resources/db/*/schema.sql`
  `code/backend/ai-training-project/src/main/resources/db/*/data.sql`
  `docs/需求/模块总表.md`
  `code/backend/DataSQL/业务变更汇总清单.md`
  `docs/workbench/data/workbench-data.js`
  `code/backend/AGENTS.md`

- 决策原因：
  保留工程骨架和公共基础设施，同时移除会误导真实项目起步的示例业务内容；空目录使用 `.gitkeep` 留住标准落点，避免后续开发重新猜目录结构。

- 风险或兼容性：
  演示接口和演示页面已不再可用，这是本次清理的预期结果。真实业务接入前，前端首页与工作台会展示空状态。

## 2026-05-14 工作台升级为 Markdown 驱动的静态进度台，并新增数据构建与手动刷新脚本

- 背景：
  第一版 `docs/workbench/` 还是手写展示数据，适合快速占位，但不能稳定反映 `docs/需求/` 中最新的需求包进度、当前步骤和责任模型，也不利于后续扩展筛选、图表和明细表。

- 变更内容：
  将工作台升级为 Markdown 驱动的静态进度台。新增 `docs/workbench/scripts/build-workbench-data.js`，用于扫描 `docs/需求/模块总表.md`、需求包 `README.md`、`实现计划.md` 和 `实现进度.md`，并生成 `docs/workbench/data/workbench-data.js`。页面本体同步改成更轻的“总览图表 + 需求包进度台 + 展开步骤明细”结构，去掉大标题式展示头图，新增“刷新页面数据”和 30 秒自动刷新选项。另补 `docs/workbench/scripts/refresh-workbench.cmd`，方便在 Windows 环境下手动刷新数据文件。

- 影响范围：
  影响 `docs/workbench/` 的数据来源和使用方式。今后工作台不再手写业务数据，而是从 Markdown 事实源构建；人类查看进度时，可以直接从工作台看到需求包当前进度、当前步骤、责任模型、风险和步骤级明细。

- 涉及文件：
  `docs/workbench/index.html`
  `docs/workbench/index.css`
  `docs/workbench/main.js`
  `docs/workbench/README.md`
  `docs/workbench/scripts/build-workbench-data.js`
  `docs/workbench/scripts/refresh-workbench.cmd`
  `docs/workbench/data/workbench-data.js`
  `docs/变更记录/CHANGELOG.md`
  `docs/变更记录/架构变更.md`

- 决策原因：
  把工作台收敛成“Markdown 为事实源、静态页为展示层、构建脚本为桥梁”的结构，能兼顾 AI 维护稳定性和人工阅读体验，也为后续继续增加需求包、步骤明细和图表指标保留扩展空间。

- 风险或兼容性：
  当前仍是静态页模式，浏览器页面本身不能直接执行本地构建脚本，因此在 Markdown 更新后，需要先运行构建脚本或双击手动刷新脚本，再回页面刷新数据。后续如果需要更接近实时的数据体验，可在此结构上再增加 watch 或本地开发服务，而不需要推翻 Markdown 事实源。

## 2026-05-14 需求文档区重构为“原始需求 + 需求包 + 模块 + 工作台”结构，并将模板迁移到 `.agents/templates`

- 背景：
  当前 `docs/需求/` 同时承载真实业务内容和 `_模板` 骨架，打开目录时容易先被模板打断注意力；同时需求输入、需求包、模块记录和人类可读总览还没有清晰分层，后续 AI 和人工查阅都容易跳来跳去。

- 变更内容：
  将 `docs/需求/` 收敛为正式业务文档区，只保留 `原始需求/`、`需求包/`、`模块/`、`模块总表.md` 和入口 `readme.md`。新增 `docs/需求/原始需求/` 用于按批次接收正式需求输入；新增 `docs/workbench/` 作为浏览器可直接打开的静态工作台；将原先 `docs/需求/_模板/` 中的需求拆分与实现计划模板整体迁移到 `.agents/templates/requirement/`，避免模板继续混在正式业务目录中。

- 影响范围：
  影响后续所有需求文档的落点方式、模板引用位置，以及人工查看需求状态时的默认入口。正式事实源仍然是 Markdown，但人类现在可以通过 `docs/workbench/` 查看总览。

- 涉及文件：
  `docs/需求/readme.md`
  `docs/需求/原始需求/`
  `docs/需求/需求包/`
  `docs/需求/模块/`
  `docs/workbench/`
  `.agents/templates/requirement/`
  `AGENTS.md`
  `docs/AI开发SOP.md`

- 决策原因：
  通过把“正式文档区”“模板区”“可视化阅读区”分层，可以同时满足 AI 稳定读写 Markdown 和人类快速浏览总览两种需求，并减少打开 `docs/需求/` 时的视觉噪音。

- 风险或兼容性：
  历史变更记录中仍会保留旧路径引用，这是文档历史的一部分，不需要回写篡改。后续新增需求包、模块和原型批次时，需要同步维护 `.agents/templates/` 和 `docs/workbench/data/catalog.js` 的对应规则。

## 2026-05-11 后端配置改为单一 Nacos dataId 承载 dev/prod 环境差异

- 背景：
  当前后端的 `application-dev.yaml` 和 `application-prod.yaml` 同时引用 `${spring.application.name}.yaml` 与 `${spring.application.name}-<profile>.yaml` 两份 Nacos 配置，但本地基础配置里没有正式启用 `spring.cloud.nacos.config` 默认项，且环境差异、本地引导配置、运行期配置分散在多份文件中，后续接入配置中心时不利于回查和统一维护。

- 变更内容：
  为 `application.yaml`、环境 profile 和数据库 profile 配置文件补充中文注释，明确“本地引导配置”和“远端运行配置”的职责边界；同时把 `dev/prod` 环境的 Nacos 引用收敛为单一 dataId `${spring.application.name}.yaml`，并新增可直接导入 Nacos 的 YAML 模板文件，通过 `spring.config.activate.on-profile` 在同一份远端配置中承载 `dev`、`prod` 差异。

- 影响范围：
  影响 `code/backend/ai-training-project` 应用模块的配置加载方式、Nacos dataId 组织方式，以及后续开发人员和 AI 补充环境配置的默认入口。

- 涉及文件：
  `code/backend/ai-training-project/src/main/resources/application.yaml`
  `code/backend/ai-training-project/src/main/resources/application-dev.yaml`
  `code/backend/ai-training-project/src/main/resources/application-test.yaml`
  `code/backend/ai-training-project/src/main/resources/application-prod.yaml`
  `code/backend/ai-training-project/src/main/resources/application-mysql.yaml`
  `code/backend/ai-training-project/src/main/resources/application-oracle.yaml`
  `code/backend/ai-training-project/src/main/resources/application-postgresql.yaml`
  `code/backend/ai-training-project/src/main/resources/nacos/ai-training-project.yaml`

- 决策原因：
  单一 dataId 更适合当前这个单应用脚手架，能减少“本地一份、Nacos 多份、环境再拆多份”的重复维护；同时把运行期可调项集中到配置中心，后续联调、运维和环境迁移时更容易定位配置来源。

- 风险或兼容性：
  `test` profile 仍保持本地配置，不依赖 Nacos；`dev/prod` 环境如果继续沿用旧的 `${spring.application.name}-dev.yaml` 或 `${spring.application.name}-prod.yaml`，需要把对应内容迁移到新的单文件模板后再删除旧 dataId，避免远端配置缺失导致运行行为与预期不一致。

- 备注：
  当前新增的 Nacos YAML 模板放在应用资源目录下，便于直接复制内容导入配置中心；如后续需要区分更多环境，可继续在同一文件中增加新的 `on-profile` 分段。
