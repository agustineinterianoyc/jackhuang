## 2026-05-19 变更记录改为结束前强制判定并直接执行，禁止只口头提示“需要记录”

- 背景：
  现有规则虽然已经明确了什么时候应该记录，但在实际执行中，模型仍容易把留痕当成“可选建议”而不是“必须完成的收尾动作”。常见表现是：先完成代码改动，再在结果里说“这个需要记录”或“要我帮你记录吗”，只有用户二次追问后才真正去更新文档，导致留痕动作不稳定。

- 变更内容：
  在 `docs/规范/变更记录规范.md` 中新增“结束前强制判定”规则，规定只要任务实际产生了变更，在宣称完成前都必须执行一次留痕判定；命中记录条件后直接更新对应文档，最终只汇报“已更新哪里、为什么记到这里”。同步收紧 `change-tracking`、`frontend-development-standard`、`backend-development-standard`，明确禁止输出“要我帮你记录吗”“是否需要我补记录”这类二次确认话术；除非用户明确要求当前轮只做分析、不改文件，否则不允许只给口头判断而不落文档。

- 影响范围：
  影响后续所有正式开发任务，尤其是前端单模块交互调整、小范围 Bug 修补、页面现象排查和联调修复类任务。今后留痕判断不再只是触发型建议，而是每次任务结束前必须执行的标准收尾步骤。

- 涉及文件：
  `docs/规范/变更记录规范.md`
  `.agents/skills/默认执行层/change-tracking/SKILL.md`
  `.agents/skills/默认执行层/frontend-development-standard/SKILL.md`
  `.agents/skills/默认执行层/backend-development-standard/SKILL.md`
  `docs/变更记录/CHANGELOG.md`
  `docs/变更记录/规范变更.md`

- 决策原因：
  仅靠任务语义触发，容易被“这是前端小调整”“先修完再说”这类执行路径绕开；把留痕变成结束前的强制判定步骤，比继续堆触发描述更稳定。这样可以把“知道应该记录”推进到“已经实际记录完成”。

- 风险或兼容性：
  本次主要收紧流程规则，不影响业务代码。后续模块级和项目级记录数量可能略有增加，但能显著降低“明知应该记录却没有落文档”的情况；如果用户明确要求当前轮只做分析，仍保留只判断不落文档的例外。

## 2026-05-19 统一后端模块级变更记录入口，并为所有变更记录文档补充顶部清单表格

- 背景：
  现有脚手架里前端已经有 `code/frontend/CHANGELOG.md`，但后端还没有稳定的模块级变更记录落点。继续按“最近模块目录就近创建”执行，容易在后端父工程下形成多个分散的 `CHANGELOG.md`，不利于统一查看。同时，`docs/变更记录/` 下各文档虽然大体按时间倒序维护，但文档开头缺少可快速浏览的清单表格，人工查看时无法一眼看到有哪些记录、对应什么日期和主题。

- 变更内容：
  将后端模块级小改动的统一落点固定为 `code/backend/CHANGELOG.md`，并要求每条记录都显式标明所属模块、服务名或应用名。同步更新 `docs/规范/变更记录规范.md`、`change-tracking`、`backend-development-standard`、`frontend-development-standard` 和模块级模板，明确前端统一写 `code/frontend/CHANGELOG.md`、后端统一写 `code/backend/CHANGELOG.md`。同时补建 `code/backend/CHANGELOG.md`，并为 `code/frontend/CHANGELOG.md`、`docs/变更记录/CHANGELOG.md`、`需求变更.md`、`架构变更.md`、`规范变更.md`、`bug修复.md`、`README.md` 增加文档开头的清单表格；对缺失日期的历史标题补齐日期，并把模板段统一放到真实记录之后。

- 影响范围：
  影响后续所有前后端模块级留痕任务，以及所有项目级变更记录文档的阅读方式。今后后端单模块改动不再在各业务目录下各自创建 `CHANGELOG.md`，而是统一记入 `code/backend/CHANGELOG.md`；阅读项目级记录时，可以先看文档顶部清单表格，再按需跳转到具体条目。

- 涉及文件：

  `docs/规范/变更记录规范.md`
  `.agents/skills/默认执行层/change-tracking/SKILL.md`
  `.agents/skills/默认执行层/backend-development-standard/SKILL.md`

  后端父工程是统一入口，模块级留痕如果继续分散到各业务目录，后续在脚手架阶段和真实项目早期都会比较难检索。统一写到 `code/backend/CHANGELOG.md` 再加模块字段，可以同时满足“后端集中看”和“知道具体是哪个模块”的诉求。文档顶部清单表格则能把“先扫一眼再决定看哪条”这个阅读动作标准化，降低查阅成本。

## 2026-05-19 明确前后端联动修复必须走 `change-tracking` 项目级留痕

- 背景：
  现有规则已经强调跨前后端改动应使用 `change-tracking`，但在实际执行中，很多任务是从“浏览器里看一下页面问题”“某个字段展示不对”“联调时有异常”这类前端现象出发。模型容易先按前端页面修复理解，再在排查过程中顺手修改后端返回字段、映射或配置，最后却仍按单端小改动收尾，漏掉项目级变更记录。

- 变更内容：
  进一步收紧 `.agents/skills/默认执行层/change-tracking/SKILL.md`，新增硬性规则：只要同一次任务同时修改了 `code/frontend/` 和 `code/backend/`，无论改动大小，默认按项目级记录处理并更新 `docs/变更记录/`。同时在 `frontend-development-standard` 中补充“页面现象或浏览器排查起步，但最终同时修改前后端时，必须补充使用 `backend-development-standard` 和 `change-tracking`”的收尾要求；在 `backend-development-standard` 中补充“若同次任务也修改了前端，则必须检查是否已补前端 skill 与项目级变更记录”；在 `skill-routing-guide` 及其 `skill-usage-checklist.md` 中新增“页面现象排查后落成前后端联动修复”的固定组合和推荐话术。

- 影响范围：
  影响后续所有从页面现象、浏览器调试、联调异常出发，最终落成前后端联动修复的任务。今后判断是否留痕，不再只看用户最初怎么描述，而是看最终实际修改面；只要同次任务同时改了 `code/frontend/` 和 `code/backend/`，就应进入项目级留痕。

- 涉及文件：
  `.agents/skills/默认执行层/change-tracking/SKILL.md`
  `.agents/skills/默认执行层/frontend-development-standard/SKILL.md`
  `.agents/skills/默认执行层/backend-development-standard/SKILL.md`
  `.agents/skills/条件触发层/skill-routing-guide/SKILL.md`
  `.agents/skills/条件触发层/skill-routing-guide/references/skill-usage-checklist.md`
  `docs/变更记录/CHANGELOG.md`
  `docs/变更记录/规范变更.md`

- 决策原因：
  遗漏留痕的核心问题不是模型不知道“跨前后端应该记录”，而是它在执行链路里没有把“从前端现象起步，最后跨端改动”视为强制升级条件。把升级条件改成“最终实际同时修改前后端”这类可观测事实，比依赖任务起点描述更稳定。

- 风险或兼容性：
  本次只调整 skill 执行规范和路由话术，不修改业务代码。后续项目级变更记录会比之前略多，但能显著减少跨端修复漏记；历史已经漏记的个案不自动回补，后续按新规则执行即可。

## 2026-05-19 `change-tracking` 收紧小改动留痕边界，明确配置修复和运行时 Bug 也应记录

- 背景：
  当前 `change-tracking` 虽然覆盖了“后续可能需要反查原因”的场景，但在“通常不使用”中仍保留了“只影响单一模块的低风险小修补”这类宽泛表述。实际执行时，模型很容易把上传大小、超时、鉴权、缓存等配置修复或运行时 Bug 修复误判为可跳过留痕的小改动，导致模块级 `CHANGELOG.md` 或项目级变更记录漏写。

- 变更内容：
  调整 `.agents/skills/默认执行层/change-tracking/SKILL.md` 的触发边界，删除“单模块小修补通常不使用”的模糊兜底，改为仅保留纯样式、纯格式、纯错别字这类无行为变化场景作为通常可跳过的范围。同步新增“生产问题或联调问题的 Bug 修复”“配置默认值修正、阈值调整、开关变更”“上传、鉴权、超时、并发、缓存、序列化等运行时行为修复”三类明确触发项，并补充单服务上传大小限制修复、单模块超时参数调整等模块级记录示例以及“是否修正了配置导致的运行时行为”收尾检查项。

- 影响范围：
  影响后续所有通过项目级 skill 处理后端配置、运行时行为修复、小范围 Bug 修补和规则留痕判断的任务。今后即使只改 1 个文件、只影响单一模块，只要存在真实行为变化且后续可能追问原因，也应至少补最近模块的 `CHANGELOG.md`；不再把“改动小”直接视为“不需要记录”。

- 涉及文件：
  `.agents/skills/默认执行层/change-tracking/SKILL.md`
  `docs/变更记录/CHANGELOG.md`
  `docs/变更记录/规范变更.md`

- 决策原因：
  小问题是否留痕，核心不在“文件数”和“改动行数”，而在是否改变真实行为、是否修复已暴露问题、以及后续是否需要回查决策原因。把触发条件写成具体行为和具体问题类型，比“低风险小修补”这类抽象判断更稳定，也更符合日常排障和联调回溯需求。

- 风险或兼容性：
  本次只收紧项目级 skill 的执行规范，不修改业务代码。后续留痕数量会比之前略多，但主要增加的是模块级 `CHANGELOG.md` 或必要的项目级规范记录，属于可接受的文档成本；历史未留痕的小修补不做追溯补录，后续按新规则执行即可。

  当前后端脚手架默认数据库 profile 是 MySQL，因此在没有额外说明时，留痕 SQL 默认按 MySQL 方言生成。

## 2026-05-11 后端数据库变更清单升级为四段式记录结构

- 背景：
  旧版业务明细模板虽然已经能记录字段、索引和 SQL，但信息重心不够突出，容易出现“看不出当前业务一共涉及哪些表”“看不出每次到底在什么时候改了什么”“单独查看某张表时还要全篇来回找”的问题。

- 变更内容：
  将 `表设计与变更记录.md` 模板调整为四段式结构：业务涉及表总览、变更流水总览、单表详细变更记录、附加说明；同时明确要求变更时间精确到分钟，并补充 `凌晨/早上/上午/中午/下午/晚上/夜间` 时段标签。单表章节下要求直接挂建表 SQL、字段/索引变更 SQL、注释 SQL、数据回填或兼容迁移 SQL。

- 影响范围：
  影响 `code/backend/DataSQL/` 下所有新增或更新的业务级数据库变更记录文档，也影响后续 AI 和开发者编写数据库留痕的默认方式。

- 涉及文件：
  `.agents/skills/database-schema-standard/SKILL.md`
  `.agents/skills/database-schema-standard/templates/business-table-change-record.md`
  `code/backend/AGENTS.md`
  `code/backend/DataSQL/...`

- 决策原因：
  让数据库留痕同时具备“按业务总览”“按时间追溯”“按单表细看”三种阅读路径，并把真正需要执行或核对的 SQL 紧贴到单表记录下面，减少信息分散。

- 风险或兼容性：
  该规范主要提升后续文档可读性和可追溯性，历史文档需要在后续修改时逐步迁移；本次已优先迁移当前已有的真实业务文档。

- 备注：
  建议后续每次数据库改动都生成变更编号，并在变更流水、单表历史和相关 SQL 校验记录中保持一致。

## 2026-05-11 后端数据库业务汇总清单升级为导航式结构

- 背景：
  旧版 `业务变更汇总清单.md` 更像一个简单的业务链接表，能看到业务名和明细链接，但看不出当前一共有多少业务目录、哪些是真实业务、最近一次是谁改了什么，也不方便从全局快速定位某条关键数据库变更。

- 变更内容：
  将汇总清单升级为导航式结构，包含文档头、汇总概览、业务清单、变更索引、待跟进事项。业务清单聚焦“当前有哪些业务、每个业务最近改了什么”；变更索引聚焦“全局最近有哪些关键数据库变更”；待跟进事项聚焦模板占位目录、待迁移和待补充说明。

- 影响范围：
  影响 `code/backend/DataSQL/业务变更汇总清单.md` 的维护方式，也影响后续 AI 和开发者从全局查看数据库变更时的默认阅读入口。

- 涉及文件：
  `.agents/skills/database-schema-standard/SKILL.md`
  `.agents/skills/database-schema-standard/templates/business-change-summary.md`
  `code/backend/AGENTS.md`
  `code/backend/DataSQL/业务变更汇总清单.md`

- 决策原因：
  让汇总清单真正承担“数据库变更导航页”的职责，先给业务覆盖面，再给最近变更，再给快速跳转路径，而不是只做一个静态目录。

- 风险或兼容性：
  该调整主要提升文档导航能力，不影响现有数据库结构或代码实现；历史汇总内容需要按新结构逐步整理。

- 备注：
  建议后续每次更新业务明细时，同步刷新汇总清单中的最近变更时间、最近变更动作和变更索引。
