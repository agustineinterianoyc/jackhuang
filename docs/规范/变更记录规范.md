# 变更记录规范

## 目标

统一判断“本次应该写模块 `CHANGELOG`，还是升级到 `docs/变更记录/`”，并保证后续人工和 AI 能回查为什么这样改。

## 记录层级

| 场景 | 记录位置 |
| --- | --- |
| 单一前端模块的小改动 | `code/frontend/CHANGELOG.md` |
| 单一后端模块的小改动 | `code/backend/CHANGELOG.md`，并在每条记录中标明模块名 |
| 需求、架构、规范、跨模块、跨前后端、重要 Bug 变更 | `docs/变更记录/` |

## 小修改判定

满足以下条件时，可只写模块 `CHANGELOG.md`：

1. 仅影响单一前端模块或单一后端模块。
2. 不改变需求口径。
3. 不改变架构边界。
4. 不改变公共规范。
5. 不跨前后端协作。

补充要求：

1. 前端模块级记录统一维护在 `code/frontend/CHANGELOG.md`。
2. 后端模块级记录统一维护在 `code/backend/CHANGELOG.md`。
3. 后端每条模块级记录必须写明所属模块、服务名或应用名，不能只写摘要。

## 结束前强制判定

只要本次任务实际产生了代码、配置、脚本、SQL、文档或规则变更，在宣称完成前都必须执行一次变更记录判定，不能跳过。

执行要求：

1. 先判断本次应写模块级 `CHANGELOG.md` 还是 `docs/变更记录/`。
2. 如果命中记录条件，直接更新对应文档。
3. 最终说明只汇报“已更新哪里、为什么记到这里”，不要停留在口头判断。

禁止行为：

1. 只回答“需要记录”或“建议记录”，但不落文档。
2. 输出“要我帮你记录吗”“是否需要我补记录”这类二次确认话术。

唯一例外：

- 用户明确要求当前轮只做分析、不要改文件时，才允许只给判断，不落记录。

## 升级为项目级记录的条件

出现以下任一条件时，必须同步更新 `docs/变更记录/CHANGELOG.md` 和分类文件：

1. 需求变更。
2. 架构或目录结构调整。
3. 公共规范或 AI 执行规则变化。
4. 跨前后端联动。
5. 影响多个模块的 Bug 修复。
6. 后续很可能需要反查“为什么这样改”。

项目级变更记录文档的排版要求：

1. 所有变更记录文档按时间倒序排列。
2. 每个文档开头都应有一张清单表格，便于快速查看日期、类型、模块和标题。
3. 模板示例必须放在真实记录之后，不能排在真实记录前面。

## 分类文件映射

| 变更类型 | 分类文件 |
| --- | --- |
| 需求 | `docs/变更记录/需求变更.md` |
| 架构 | `docs/变更记录/架构变更.md` |
| 规范 | `docs/变更记录/规范变更.md` |
| Bug | `docs/变更记录/bug修复.md` |

## 项目级记录最小字段

详细记录至少包含：

1. 背景
2. 变更内容
3. 影响范围
4. 涉及文件
5. 决策原因
6. 风险或兼容性说明

如果是 Bug 修复，额外补已知根因。

## 与其他规则的边界

1. 需求拆分、需求包计划和模块长期记录由 `docs/需求/` 承担，不由变更记录替代。
2. 数据库结构和 SQL 留痕由 `code/backend/DataSQL/` 承担，不由变更记录替代。
3. 变更记录回答“为什么改、影响什么、后续从哪继续看”。

## 触发 skill

当本规范命中项目级记录条件时，优先使用 `change-tracking`。
