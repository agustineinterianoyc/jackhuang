# 需求管理规范

## 目标

统一正式需求输入、模块命名、需求包计划和模块长期记录的组织方式，避免同一业务能力在文档、后端目录和 DataSQL 中各用一套名字。

## 正式事实源

`docs/需求/` 是正式业务需求事实源，承担四类内容：

1. `原始需求/`
   接收正式需求输入。
2. `模块总表.md`
   记录模块中文名、模块编码、后端目录名和 DataSQL 目录名，是唯一命名事实源。
3. `需求包/`
   记录一批需求、一个版本或一次迭代的整体实现计划。
4. `模块/`
   记录单个业务模块的长期演进。

## 批次输入规则

每批正式需求建议采用：

```text
docs/需求/原始需求/<批次目录>/
├── 批次说明.md
└── *.md
```

规则：

1. `批次说明.md` 是 AI 判断“小改动 / 阶段性变更 / 新需求包”的首要锚点。
2. 正式需求拆分前，先同时读取 `docs/需求/原始需求/<批次>/` 和 `docs/原型/<批次>/`。
3. `docs/原型站点/` 是原型站点产出目录，不作为正式需求拆分输入根。

## 模块总表规则

新增业务模块前，先查 `docs/需求/模块总表.md`。

规则：

1. 模块编码跨需求包保持稳定。
2. 命中已有模块时继续复用原模块编码，不重复创建近义模块。
3. 后端业务目录、测试目录、Mapper XML 目录和 DataSQL 目录优先按模块总表取名。
4. DataSQL 目录名优先使用模块中文名，并在模块总表登记。

## 需求包规则

每个需求包统一使用：

```text
docs/需求/需求包/<需求包目录>/
├── README.md
├── 实现计划.md
├── 实现进度.md
└── 接口清单.md
```

规则：

1. `README.md`、`实现计划.md`、`实现进度.md` 为统一必备文件。
2. `接口清单.md` 只在涉及前后端联动时必需维护。
3. 需求包计划优先按业务闭环拆步骤，不先机械拆成互相割裂的“前端计划”和“后端计划”。

## 模块目录规则

每个模块建议包含：

```text
docs/需求/模块/<模块中文名>/
├── README.md
├── 需求实现记录.md
├── 需求实现优化调整记录.md
└── 数据库留痕索引.md
```

规则：

1. 模块目录负责长期演进，不重复承担需求包职责。
2. `数据库留痕索引.md` 只记录 DataSQL 链接、表摘要和变更编号，不重复维护完整 SQL。

## 与后端目录和 DataSQL 的关系

1. 后端业务代码按模块编码建立子目录。
2. DataSQL 业务目录优先使用模块总表中的 DataSQL 目录名。
3. 需求模块文档只引用 DataSQL，不重复维护完整 DDL 和字段清单。

## 何时触发需求拆分 skill

出现以下任一情况时，优先使用 `requirement-implementation-tracking`：

1. 新批次需求或原型输入进入项目。
2. 需要新增模块、复核模块边界或建立新的需求包计划。
3. 需要把前端页面、后端接口、数据库变更和联调状态收敛到同一份计划中。

如果只是对已有模块做小范围实现修改，且现有需求包和模块记录已足够清楚，不要求重复触发该 skill。
