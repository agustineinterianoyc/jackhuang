## 2. 评审摘要

### 2.1 本次数据库设计目标

- 用最小可行表集合承载意见征集主流程：征集任务 → 基层填报 → 基层审核 → 专业反馈 → 专业审核 → 汇总 → 发布。
- 状态字段使用枚举常量；主流程主状态 + 各阶段子状态分开存储（主状态共 6 个，与原型确认的状态筛选下拉一致）。
- 附件、提醒、审计日志、汇总采纳清单独立成表，避免主表过宽。
- 与项目级数据库规范（前缀 `ad_`、逻辑删除、审计字段）保持一致。

### 2.2 数据库变更结论

- **新增表**（13 张，全部已在 schema.sql 落地）：
  - `ad_opinion_survey`、`ad_opinion_survey_module`、`ad_opinion_survey_target`
  - `ad_opinion_unit_task`、`ad_opinion_item`、`ad_opinion_unit_audit_log`
  - `ad_opinion_dept_task`、`ad_opinion_feedback`、`ad_opinion_dept_audit_log`
  - `ad_opinion_summary_item`
  - `ad_opinion_attachment`、`ad_opinion_reminder_log`
  - `ad_opinion_action_log`
- **调整表**：无
- **延用表**：无（首次实现，组织 / 用户 / 文件等主数据通过外部接口或既有表只读引用）
- **废弃表**：无

### 2.3 需要评审确认的关键点

| 评审点 | 推荐方案 | 风险 | 对开发的影响 |
| --- | --- | --- | --- |
| 单位 / 部门主数据存储 | 仅落 `unit_id` / `department_id`（外部主数据 ID）+ 名称冗余 | 没有外键，依赖外部主数据稳定 | 影响 R02–R05 数据隔离实现 |
| 意见行（`ad_opinion_item`）与指标体系的关联 | 仅保存 Tab + 指标定位字段（如指标名称、因子名称、考核内容等冗余字段），不直接关联指标主数据 | 指标体系仍是非结构化附件 | 决定 P02 / P03 / P04 / P05 详情页字段渲染 |
| 多轮次承载 | 不引入 `round / batch` 字段，多轮次通过新建征集任务承载 | 后期若要"轮次内对比"需要扩表 | 简化当前设计 |
| 附件方案 | `ad_opinion_attachment` 仅存元数据 + `file_id`，物理文件由项目通用文件服务管理 | 文件服务接口未定 | 附件接口契约待定 |
| 状态字段类型 | 统一 `VARCHAR(32)`，使用业务枚举常量 | 不使用 SMALLINT，排查可读 | 实现简单 |
| 「调整后内容」长度 | `VARCHAR(1000)` | 若客户要求 ≥1000，需要扩到 TEXT | 决定列长度 |

## 11. 数据库实现约束

> 本节只保留能直接约束数据库实现的表、字段、枚举、迁移和兼容规则。

### 11.1 不可改变的数据库约束

- 表前缀统一 `ad_opinion_`。
- 主键统一 `BIGINT UNSIGNED AUTO_INCREMENT`。
- 状态字段统一 `VARCHAR(32)`，禁止 SMALLINT；枚举常量见 §7。
- 主状态共 6 个，禁止再扩展「待发布」主状态。
- 所有表必须包含 `deleted_flag` + `created_at` + `updated_at`，逻辑删除统一 `deleted_flag`。
- 不创建物理外键，仅在应用层维护一致性。
- 字符集 `utf8mb4`，排序 `utf8mb4_general_ci`。
- 时间字段统一 `DATETIME`（精度到秒）。
- 单位 / 部门 / 用户 ID 一律存为 `BIGINT`，并冗余必要的名称快照字段。
- 唯一约束需带 `deleted_flag`，避免逻辑删除后冲突。
