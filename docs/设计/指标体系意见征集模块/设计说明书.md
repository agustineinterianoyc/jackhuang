## 2. 评审摘要

### 2.1 本次设计目标

- 把 V2.1 业务需求 + 原型站点事实整理成可评审、可约束实现的设计基线。
- 状态机锁定为「6 个主状态 + 4 套子状态」（原型确认主状态共 6 个，"待发布"是「已完成」状态下的一个 UI 子页面，不再单独建主状态）。
- 输出统一的后端枚举常量 + 原型 key + 中文展示文案三栏映射，避免后端 / 前端 / 文档三处出现不一致。
- 给后续后端模块、数据库设计、接口清单、实现计划提供同一套术语与编码。

### 2.2 设计结论

- **业务模块编码**：`opinion`（指标体系意见征集模块），所有前后端目录、表前缀、接口前缀、菜单 P 编码均围绕该编码组织。
- **菜单层级**（确认自原型 menu.js）：
  - 一级菜单：业务考核（`performance`）
  - 二级菜单：指标体系意见征集模块（`opinion-collect`）
  - 三级菜单：P01 ～ P05（与需求 P0101 ～ P0105 编号语义对应）
  - 同级还有 4 个本模块外的占位菜单：工作台、合同签订、指标体系修订、季度考核、年度考核（不在范围内）
- **状态机模型**（双层状态）：
  - **主状态（6 个，落 `ad_opinion_survey.status`）**：`DRAFT / WAIT_FILL / FILLING / DEPT_FEEDBACK / DONE / PUBLISHED`
  - **基层填报子状态**：`PENDING / SUBMITTED`
  - **基层审核子状态**：`NONE / PENDING / PASS / REJECTED`
  - **专业提交子状态**：`PENDING / SUBMITTED`
  - **专业审核子状态**：`NONE / PENDING / PASS / REJECTED`
  - **「待发布」**不作为主状态，而是「已完成（DONE）」状态下的发布汇总页 UI 子状态（在汇总页内由按钮「发布」推进至 PUBLISHED）。这与原型 P01 列表状态筛选 6 项口径完全一致。
- **数据组织**：以「征集任务（survey）→ 征集模块（module，5 类指标 Tab）→ 基层任务（unit_task）→ 基层意见（item）→ 专业反馈（feedback）→ 汇总调整（summary_item）」为核心实体链。
- **角色权限**：5 个业务角色按「单位维度 + 部门维度」做数据隔离，绩效管理员（R01）拥有全局视图。
- **附件管理**：附件统一接入项目级「文件服务」（待确认），落地时仅保存文件 ID + 元数据。
- **零报送机制**：基层截止时间到达后由定时任务执行「自动空数据提交 + 自动审核通过」；专业截止时间到达后仅触发提醒，不自动提交。
- **三栏枚举映射**：所有状态、Tab、部门、意见分类都在《数据库设计说明书》§7 定义"后端常量 → 原型 key → 中文展示"三栏映射，作为前后端联调真源。

### 2.3 与需求 / 原型的差异点（已落实结论）

| 差异点 | 需求口径 | 原型口径 | 设计结论 |
| --- | --- | --- | --- |
| 主状态个数 | 7 个（含「待发布」） | 6 个（不含独立的「待发布」） | **采用 6 个**：「待发布」改为 DONE 主状态下的发布汇总页子状态 |
| Tab 模块编码 | 中文（关键业绩指标 / 业绩争取加分等） | 英文 key（performance / bonus / party / safety / other） | **后端枚举使用 `KPI / BONUS / PARTY / SAFETY / OTHER`**；原型 key 仅作前端与后端 ↔ 原型对照映射 |
| P03 / P05 退回状态 | 中文「已退回」 | P03 用 `returned`、P05 用 `rejected`（同语义两套 key） | **后端统一 `REJECTED`**；前端按设计枚举发请求与展示，原型 key 仅作映射参考 |
| 部门枚举 | 文字描述 | menu.js 列 4 类（finance/development/publicity/safety），P01 进度表数据列 5 个（财务部、发展部、党委宣传部、安监部、设备部） | **不在 schema 中固化部门字典**；按主数据 `department_id` 引用，部门列表由组织主数据提供 |
| 「调整后内容」展示 | 汇总发布页字段 | 仅在 P02/P05 状态为 `published` 时多出列 | 设计中作为 `ad_opinion_summary_item.adjusted_content`；P02/P05 已发布态读视图共用此字段 |

### 2.4 需要评审确认的关键点

| 评审点 | 推荐方案 | 备选方案 / 风险 | 对开发的影响 |
| --- | --- | --- | --- |
| 单位 / 部门主数据来源 | 接入既有组织主数据（待项目方提供接口或字典） | 项目内独立维护单位字典 | 决定 R02–R05 数据隔离实现方式 |
| 文件存储方案 | 复用项目通用文件服务（接口待确认） | 模块自建落盘存储 | 决定附件表是否需要保存物理路径 |

| 多轮次 / 分批次的承载方式 | 通过新建征集任务承载（征集名称示例「2026年第一轮第一批次意见征集」与原型一致） | 引入显式 round / batch 字段 | 决定状态机是否需要回到上一阶段 |
| 一键提醒下发渠道 | 复用项目通知中心（待确认） | 仅做站内消息 | 决定通知接口契约与异步处理 |

| 同一基层单位是否多人填报 | 同一时间仅一人填报，按用户 ID 锁定（推荐） | 多人协同填报 | 决定填报详情页与意见行的并发策略 |
| 部门 ↔ 模块映射来源 | 项目内字典维护（推荐）；后期可改为主数据驱动 | 部门勾选模块 | 决定 `ad_opinion_dept_task` 的初始化逻辑 |

## 3. 范围与边界

### 3.1 范围内

- P01 意见征集管理（绩效管理员）— 含主列表、新增 / 编辑、查看、发布汇总页、基层进度弹窗、专业反馈进度弹窗、删除确认、开启征集确认 4 个弹窗
- P02 基层单位意见征集（基层绩效管理员）— 含主列表、填报详情、查看详情、提交确认、提交成功 2 个弹窗
- P03 基层单位意见征集审核（基层人资部主任）— 含主列表、审核详情、查看详情、审核确认、退回确认 2 个弹窗
- P04 专业部门反馈（专业绩效联络员）— 含主列表、反馈详情、查看详情、提交确认 1 个弹窗
- P05 专业部门反馈审核（专业部门负责人）— 含主列表、审核详情、查看详情、审核确认、退回确认 2 个弹窗
- 5 类指标 Tab 的 Tab 化展示与字段差异
- 主流程 10 节点 + 双向退回 + 零报送 + 通知触发点
- 一键提醒、单条提醒、按单位/部门维度的进度查询弹窗
- 列表筛选、查询、清空条件、分页（10/20/50/100 条 / 页）、导入、导出

### 3.2 范围外

- 指标体系附件本身的内容解析（系统仅做附件挂载，不做指标结构化解析）
- 一级菜单"工作台、合同签订、指标体系修订、季度考核、年度考核"全部业务（菜单占位但不实现）
- 单位 / 部门 / 用户主数据维护页面
- 角色与用户权限维护页面
- 全局通知中心 / 待办中心实现（仅作为依赖）
- 数据可视化看板、统计报表
- 移动端适配（需求要求 PC 端 16:9 自适应即可）

### 3.3 默认假设

- 单位、部门、用户、角色等主数据由系统其他模块或外部主数据系统提供，本模块只读引用
- 文件上传 / 下载走项目通用文件服务，本模块仅持有文件 ID
- 项目时区为 `Asia/Shanghai`，所有时间字段精确到秒
- 列表排序默认按 `创建时间 DESC`，符合需求 6.2 第 1 条
- 删除均为逻辑删除（需求 6.2 第 3 条），统一使用 `deleted_flag` 字段
- 提交动作均「先保存再提交」（需求 6.2 第 4 条）
- 单行文本限制 50 字、多行文本限制 260 字（需求 6.2 第 6 条）；调整后内容默认 1000 字（待评审）
- 浏览器要求 Chrome / 国家电网（GW）浏览器（需求 6.2 第 18 条）
- 每页条数下拉固定 10 / 20 / 50 / 100（原型确认）

## 5. 业务流程与状态规则

### 5.1 主流程（与需求 4.1 节点表完全对齐）

1. **创建征集（节点 10 / DRAFT）**：R01 在 P01 创建征集任务（基本信息 + 征集对象 + 征集模块 + 模块附件）。
2. **开启征集（节点 20 / WAIT_FILL）**：R01 二次确认后开启，状态推进到 `WAIT_FILL`，触发基层通知，征集信息变为只读。
3. **基层填报（节点 30 / FILLING）**：R02 在 P02 下载附件、逐条填报、提交。提交后子状态为 `SUBMITTED`。
4. **基层审核（节点 40 / FILLING）**：R03 在 P03 通过 / 退回。退回触发基层重新填报；通过后审核子状态为 `PASS`。
5. **开启专业反馈（节点 50 / DEPT_FEEDBACK）**：R01 在 P01 二次确认开启，前置条件为「全部基层已审核通过」；开启后基层不可再退回。
6. **专业反馈（节点 60 / DEPT_FEEDBACK）**：R04 在 P04 逐条决策是否采纳并填写采纳说明，提交。
7. **专业审核（节点 70 / DEPT_FEEDBACK）**：R05 在 P05 通过 / 退回。
8. **绩效汇总（节点 80 / DONE）**：全部专业审核通过后进入 `DONE`，等待 R01 汇总。
9. **绩效调整（节点 90 / DONE，UI 子状态：待发布）**：R01 在汇总页确认采纳并补充「调整后内容」。
10. **发布（节点 100 / PUBLISHED）**：R01 二次确认发布，所有退回 / 编辑功能关闭，通知所有基层。

### 5.2 关键分支 / 异常流

| 场景 | 触发条件 | 处理规则 | 用户可见结果 | 后续影响 |
| --- | --- | --- | --- | --- |
| 基层退回 | R03 在节点 40 选择「退回」 | 主状态保持 `FILLING`，基层审核子状态置 `REJECTED`，记录退回原因；R02 看到退回提示后重填 | R02 可重新提交；通知 R02 | 不允许在主状态非 `FILLING` 时退回 |
| 绩效管理员对基层退回 | R01 在主状态 `FILLING` 时执行「绩效退回基层」 | 与基层人资部主任退回同效果，但发起方为 R01 | R02 可重新提交；通知 R02 | 仅在主状态 `FILLING` 时可触发 |
| 专业退回 | R05 在节点 70 选择「退回」 | 主状态保持 `DEPT_FEEDBACK`，专业审核子状态置 `REJECTED` | R04 可重新提交 | 仅在主状态 `DEPT_FEEDBACK` 时可触发 |
| 绩效管理员对专业退回 | R01 在发布前执行「绩效退回专业」 | 主状态保持 `DEPT_FEEDBACK`，重置 R04 与 R05 子状态 | R04 重新反馈、R05 重新审核 | `PUBLISHED` 后不可触发 |
| 基层零报送 | 基层截止时间到达 | 系统将未提交单位置为「已提交（空数据）」并自动通过审核（落 `auto_zero_report=1`） | 视为「已审核」 | 不再触发退回 |
| 专业截止超时 | 专业截止时间到达 | 仅向 R04 / R05 发送提醒，不修改状态 | 提醒显示在通知中心 | 状态需人工继续推进 |
| 一键提醒 | R01 在进度弹窗触发 | 后端按当前未提交集合下发提醒；记录 `reminder_log`；同一目标 5 分钟内不重复发通知（频控由后端实现） | Toast 提示「已提醒：{N} 个未提交单位」（其中 X 个 5 分钟内已提醒，本次跳过） | 同一单位 5 分钟内不重复发通知 |
| 字段超长 | 输入超过 260 字 | 前端阻止 + 红色提示；后端做 length 校验兜底 | 表单错误 | 不入库 |
| 重复提交 | 同一任务重复 POST 提交 | 通过 `survey_id + role + actor_id + 当前状态` 幂等 | 第二次返回当前状态而非报错 | 防双击 |

### 5.3 状态流转

> 主状态共 6 个：`DRAFT`、`WAIT_FILL`、`FILLING`、`DEPT_FEEDBACK`、`DONE`、`PUBLISHED`。

| 对象 | 当前状态 | 触发动作 | 下一状态 | 规则说明 |
| --- | --- | --- | --- | --- |
| 征集任务（survey） | `DRAFT` | R01 [开启征集] | `WAIT_FILL` | 必须配置征集对象与征集模块；初始化 `ad_opinion_unit_task` |

### 8.1 权限规则

| R05 专业部门负责人 | P05 | 仅本部门 | 审核（通过 / 退回） | — |

### 8.2 数据边界

- **数据来源**：组织主数据（单位 / 部门 / 用户）只读引用；征集任务等业务数据由本模块管理。
- **数据可见范围**：R02 / R03 按 `unit_id` 隔离；R04 / R05 按 `department_id` 隔离；R01 全量。
- **数据修改边界**：状态推进后旧阶段字段冻结（详见状态流转）；逻辑删除统一通过 `deleted_flag`。
- **历史数据兼容**：本次为首次实现，无存量数据迁移；后续年度征集独立任务并按 `assess_year` 隔离。

### 8.3 安全要求

- **身份认证**：沿用项目网关层 JWT；未登录访问统一 401。
- **敏感数据**：暂未识别敏感字段（待评审确认）。
- **日志审计**：开启征集 / 提交 / 审核 / 退回 / 发布 / 一键提醒等动作落审计日志。
- **特殊字符**：所有文本输入按需求 6.2 第 13 条做白名单转义。

## 9. 技术实现方案

### 9.1 前端设计

- **页面 / 组件**：基于现有 Layout（顶部 + 侧边 + 主区），新增 `views/opinion/` 目录，按 P01–P05 拆分页面；公用组件抽离 `components/opinion/`（进度弹窗、Tab 容器、退回弹窗、提交确认弹窗、附件上传组件）。
- **路由**：`/opinion/survey`（P01）、`/opinion/unit-fill`（P02）、`/opinion/unit-audit`（P03）、`/opinion/dept-feedback`（P04）、`/opinion/dept-audit`（P05），每条路由对应一个 P 编号。
- **状态管理**：每个二级菜单一个 Pinia store；列表查询、Tab 切换、详情草稿暂存均放入 store。
- **API 调用**：统一通过 `utils/request.ts` 封装；按模块拆 `api/opinion/{survey,unitFill,unitAudit,deptFeedback,deptAudit,progress,summary,attachment}.ts`。
- **枚举映射**：`@/constants/opinion.ts` 维护「后端常量 → 中文展示文案 → 原型 key」三栏映射，前端发请求/展示均从此读取。
- **兼容性要求**：Chrome / GW 浏览器；分辨率 1366×768 起自适应。

### 9.2 后端设计

- **Controller**：按子模块拆 controller，统一前缀 `/api/opinion/...`。
  - ✅ 已实现：`OpinionSurveyController`（P01）、`OpinionUnitFillController`（P02）、`OpinionUnitAuditController`（P03）、`OpinionAttachmentMockController`（附件挂载 Mock）、`OpinionDictController`（字典查询 Mock）

- **Service**：状态机集中在 `OpinionStateMachine` 单例，所有状态推进 / 退回必须通过它，禁止 service 直接 update 状态字段。
  - ✅ 已实现：`OpinionStateMachine`、`OpinionSurveyService`、`OpinionUnitFillService`、`OpinionUnitAuditService`、`OpinionActionLogger`、`OpinionMockMasterDataProvider`
  - ❌ 待实现：`OpinionDeptFeedbackService`、`OpinionDeptAuditService`、`OpinionProgressService`、`OpinionReminderService`、`OpinionSummaryService`

- **定时任务**：基层零报送 / 专业截止提醒 走 Spring `@Scheduled`，每 5 分钟扫描一次。
  - ✅ 已实现：`OpinionAutoZeroReportJob`（零报送定时任务）

## 12. 开发约束摘要

### 12.1 开发约束

- **不可改变的业务规则**：
  - 主状态共 6 个，禁止再增加「待发布」主状态。
  - 基层退回仅在主状态 `FILLING` 时允许；专业退回仅在 `DEPT_FEEDBACK` 且 `PUBLISHED` 前允许。
  - 「开启专业反馈」前置必须是「全部基层已审核通过」。
  - 发布后所有写操作禁用。
  - 基层截止时间到达后系统必须自动空提交并自动审核通过；专业截止时间到达后只能提醒。
  - 退回原因、采纳说明（采纳时）、意见内容、原因说明均落 260 字上限；调整后内容默认 1000 字。
  - 删除统一逻辑删除（`deleted_flag`），并需二次确认。
- **不可改变的数据结构**：
  - 表前缀统一 `ad_opinion_`，遵循项目级前缀规范。
  - 基层任务、专业任务、意见、反馈、审核日志、提醒日志的主键统一 `BIGINT UNSIGNED AUTO_INCREMENT`。
  - 状态字段统一 `VARCHAR(32)`，使用枚举常量类，禁止散落字符串。
  - 后端枚举常量为权威：状态采用 `DRAFT/WAIT_FILL/FILLING/DEPT_FEEDBACK/DONE/PUBLISHED`、`PENDING/SUBMITTED`、`NONE/PENDING/PASS/REJECTED`；模块编码 `KPI/BONUS/PARTY/SAFETY/OTHER`。
- **不可改变的接口契约**：
  - 接口前缀 `/api/opinion/...`，子路径与模块编码一致。
  - 列表查询统一 `POST /list`（带筛选体）+ 分页字段 `page/pageSize`，每页可选 10/20/50/100。
  - 状态推进类接口统一返回最新主状态 + 子状态。
  - 接口编号 API-101 起按本设计文档编号约定。
- **编码 / 架构约束**：
  - 业务代码默认放在 `code/backend/aldemohk/`，按 `controller/opinion`、`service/opinion`、`repository/opinion`、`model/{request,response,vo,dataobject}/opinion`、`mapper/opinion` 子目录组织。
  - 状态机集中在 `service/opinion/state/OpinionStateMachine.java`。
  - DataSQL 留痕落 `code/backend/DataSQL/opinion/`。
